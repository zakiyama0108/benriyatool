> **着手前チェック(重複作業の防止):** `git fetch origin main` でローカルmainの遅れを確認し、遅れていれば先に最新化する。続けて `gh pr list --state all --limit 20 --search "<対象のアプリ名や機能名>"` と `git ls-remote --heads origin` で、同じspec・同じ機能を扱う既存PR(オープン=進行中 / マージ済み=対応済み)や進行中ブランチ([parallel-work](../parallel-work/SKILL.md)の着手宣言)がないか確認し、見つかったら作業を始めずユーザーに報告する(この項は requirement/design/fix/implementation の4Skillに同文で記載。変更時は揃って更新する)

# Step0 入口の判断: 新規spec作成 vs 既存spec更新

機能に着手する前に、新しい`specs/<アプリ名>/<機能名>/`フォルダを作るか、既存specを更新するかをまず判断する。ここを誤ると、既存機能の修正が別機能のspecとして切り出され、同じビジネスルールが複数のrequirements.mdに分散してしまう。

**既存specを更新すべきサイン**(いずれか1つでも該当したら新規フォルダを作らず[/fix](../fix/SKILL.md)のフローへ切り替える):
- 既存のユーザーストーリー・機能要件・ビジネスルールの一部を書き換える/追記するだけで説明が済む
- 実装が既存specの対象ファイル・関数を修正するものである(新しいファイルの追加だけで完結しないなら既存spec寄り)
- 機能名が「〜への〜追加」「〜の修正」のように既存機能名や既存の入出力を前提にしている(強いシグナル)
- 既存specの「スコープ外」にあった項目に今回対応する、または既存の計算誤り・バグを直す

**新規specを作るべきサイン**(本Skillで進める):
- 新しい画面・新しいURL・独立してリリース/ロールバックできる機能である
- 既存のユーザーストーリーでは説明できない、新しい利用者視点の目的がある
- 別のドメイン・別のデータストアなど、技術的に独立した関心事である(例: `save-result`は計算ロジックではなくDB保存という別関心事のため独立spec)

> 「新規specを作るべきサイン」の3項目は[/fix](../fix/SKILL.md)のStep1に要約が転記されている(/fix単体で判断を完結させ、本Skillの読み込みを省くため)。変更時は両方を更新する。

# 新規アプリ立ち上げ時のspec分割

新しいアプリに着手するときは、要件を1つの巨大なspecフォルダにまとめない。まず利用者視点のユーザーストーリー(「〜としては、〜したい」)を洗い出し、**1ストーリー=1specフォルダ**を原則に`specs/<アプリ名>/<機能名>/`を縦に分割して作る。

- 洗い出したストーリーの数だけ`specs/<アプリ名>/<ストーリーを表す機能名>/`を並べて作る(例: 育休給付金シミュレーターなら`maternity-benefit`(出産手当金)、`paternity-leave-benefit`(産後パパ育休)、`childcare-benefit-early`(育休前期67%)、`childcare-benefit-late`(育休後期50%)、`input-form`(入力フォーム)、`payment-schedule`(振込スケジュール)のように分ける)
- 複数のストーリーの結果を1つの画面にまとめる(合計金額表示・内訳バーなど)統合ロジックが必要な場合は、新たに統合専用specを作らず、その統合先(最終的にユーザーが見るメイン画面)を担当するstory specに書く。他のstory specの機能要件には「この結果は`<まとめ先の機能名>`の画面で使われる」と一言添えて依存関係を明示する
- アプリ立ち上げ時は`specs/<アプリ名>/architecture.md`も最初から作成する(作成基準・書き方は[architecture-workflow](../architecture-workflow/SKILL.md)を参照)
- あわせてリポジトリ直下[README.md](../../../README.md)の「アプリ一覧」テーブルに1行追加する(アプリ名・パス・概要・architecture.mdへのリンク)
- 各specが育ってきて「既存機能の修正・拡張」に該当する変更が発生したら、以降は上記Step0の判断に従う

# 要件ヒアリング

requirements.mdを書き始める前に、以下の4項目が**すべて**確認できているかを確認し、足りないものはユーザーに質問して埋める。

- 誰のための機能か(ユーザーストーリーの主語)
- 何ができればよいか(入出力・画面の完成イメージ)
- ビジネスルールと根拠(数値・条件は法令・公式資料などの出典とセットで確認する)
- 今回やらないこと(スコープ外)

**聞き方**: 一度に全部聞かず、重要な順に1〜2項目ずつ質問する。回答を受け取ったら、残りの項目がまだ埋まっていないか都度確認し、埋まっていなければ続けて質問する(往復して構わない)。ユーザーの最初のメッセージだけで書き始めず、4項目が出揃うまでrequirements.mdの作成に進まない(未確認のまま推測で埋めてよいのは[/autopilot](../autopilot/SKILL.md)の推測マーカー運用が対象とする設計の細部のみで、この4項目は対象外)。

**新しい画面を追加する場合**: 「何ができればよいか」の確認で新しい画面・表示の追加が分かったら、文章だけで質問を返さない。ラフなワイヤーフレーム(テキスト/ASCIIで十分、Figma等の外部ツールは使わない)をレイアウト案として複数作成し、AskUserQuestionの`preview`機能で並べて提示してから選んでもらう。画面イメージのすり合わせは文言だけのやり取りよりユーザーとの認識のズレを防げる([/autopilot](../autopilot/SKILL.md)の対話①でも同様に適用する)。

# requirements.mdの書き方

「何を作るか(WHAT)」「なぜその仕様にしたか(根拠)」を言語化する。数式・変数名は使わず日本語の言葉で書く(正確な計算式はコードとテストに委ねる)。技術的な実装方法(HOW)はここでは書かない。

タイトル直下に `> ステータス: 仕様確認中(未実装)` という行を入れる(この行の意味と削除タイミングは[/pr](../pr/SKILL.md)の仕様承認ゲートを参照)。

以下の見出しをテンプレートとして使う(該当しないものは省略してよい)。

1. **概要** — 機能名・目的・優先度
2. **ユーザーストーリー** — 「〜としては、〜したい」という利用者視点の要求
3. **機能要件** — 実装する機能と入出力を言葉で説明する
4. **ビジネスルール・制約** — 数値・条件などのルールと、その根拠(法令・公式資料・過去の意思決定など)を必ずセットで書く。特殊な入力やエラー時にどう振る舞うべきかも、条件付きのルールとしてこの見出しの中に書く(例:「賃金日額が上限を超える場合、上限額を基準に計算する」)。項目が複数ある場合は`###`見出しで分ける(テストとの対応付けがしやすくなる)
5. (任意)**非機能要件・依存関係・制約条件・UI/UX要件** — 関係する場合のみ書く。無理に埋めない。
   依存関係を書く際、他specの機能要件・ビジネスルールの入出力をそのまま使う場合は内容を書き写さず、`<spec名>/requirements.md#見出し-n`の形で参照する(書き写すと元specが変更されたときに追随できなくなる)

## [n]採番ルール

機能要件・ビジネスルール・制約など、個別にテストを対応させたい箇条書きには見出し内で連番の`[n]`を振る(見出しが変わればまた`[1]`から振り直してよい、グローバルな採番ではない)。

```markdown
### 出産手当金
- [1] 対象: ママのみ
- [2] 対象期間: 出産予定日の42日前(産前)から出産日の56日後(産後)までの98日間
- [3] 給付額: 対象期間中、賃金日額の3分の2を支給する
```

概要・ユーザーストーリー・スコープ外など、そもそもテスト対象にならない見出しには`[n]`を振らなくてよい(見出し単位でスキップ登録の対象になる)。

箇条書きは「〜の場合、〜になること」という文体に揃えておくと、そのままテストの`it()`に転記しやすい。
