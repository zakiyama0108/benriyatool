> ワークフロー上の位置: **/fix(本Skill)** → [/implementation-review](../implementation-review/SKILL.md) → [/pr](../pr/SKILL.md)(実装PR)

> **次フェーズのモデル:** 基本は **Sonnet**(トークン消費を抑えるため下流工程は原則Sonnetで運用する)
> - Step2で仕様変更が必要と判定した場合: 複数のビジネスルール変更・法令改正への適合など影響範囲の特定が重要な場合のみ **Opus** を検討する
> - 純粋なバグ修正の場合: 複雑なバグ・複数箇所の修正が必要な場合のみ **Opus** を検討する

> **着手前チェック(重複作業の防止):** `git fetch origin main` でローカルmainの遅れを確認し、遅れていれば先に最新化する。続けて `gh pr list --state all --limit 20 --search "<対象のアプリ名や機能名>"` と `git ls-remote --heads origin` で、同じspec・同じ機能を扱う既存PR・進行中ブランチがないか確認する。該当しそうなブランチ/PRが複数見つかった場合は、PR本文・ブランチ名を`specs/<アプリ名>/<機能名>/`のパスで絞り込む。それでも複数残る、またはどれが自分の続きか判断できない場合は、推測でどれかを選ばず候補一覧をユーザーに提示して確認する。1件に絞れた場合、それが「自分がこれから進める工程の一つ前の工程が作ったもの」(例: /requirementが作った`feature/<機能名>`ブランチに/designで続きを積む場合)であればそれは重複ではないので、そのブランチをcheckoutして続行する。それ以外(既に先の工程まで進んでいる、または別セッション・別人の作業)は作業を始めずユーザーに報告する(この項は requirement/design/fix/implementation の4Skillに同文で記載。変更時は揃って更新する)

# Step1 入口の確認

今回の変更が**既存spec更新**(本Skillの対象)であることを確認する。以下の**新規specを作るべきサイン**に1つでも該当したら、本Skillではなく[/requirement](../requirement/SKILL.md)のフローへ切り替える:

- 新しい画面・新しいURL・独立してリリース/ロールバックできる機能である
- 既存のユーザーストーリーでは説明できない、新しい利用者視点の目的がある
- 別のドメイン・別のデータストアなど、技術的に独立した関心事である

いずれにも該当しなければそのままStep2へ進む。判断に迷う場合のみ、/requirementのStep0「新規spec作成 vs 既存spec更新の判断」を読んで判断する(上記3項目はStep0の要約。Step0側を変更したらここも追随する)。

# Step2 仕様(3点セット)への影響を洗い出す

既存specを更新する場合、3点セットすべてへの影響を洗い出す。1つのファイルだけ直して終わりにしない。

- **requirements.md**: 該当する見出しの`[n]`を書き換える、または新しい`[n]`を追記する(既存の連番は崩さない)。エッジケース・スコープ外に古い記述が残っていないか確認する
- **design.md**: 処理フローの該当する処理を更新する。処理の呼び名・手順が変わった場合は書き直す。埋め込まれているMermaid図(シーケンス図・状態遷移図)が変更後の文章とずれる場合は、同じ変更で図も更新する(図だけが古くなることの禁止)
- **tasks.md**: 新しいタスクとして追記する(過去タスクの完了チェックは履歴として残し、変更しない)

さらに、仕様書だけでなく実装・テストへの影響も必ず洗い出す:

- 実装コード(該当する`app/`配下のファイル)のどこを変更する必要があるか
- 既存テストの`// 仕様: specs/.../requirements.md#見出し-n`コメントが指す見出し・`[n]`がずれないか(見出し名や番号を変更したら、対応するテストコメントも合わせて書き換える)
- `npm run check:spec-coverage`を実行し、新旧の対応関係が壊れていないか確認する
- `specs/<アプリ名>/architecture.md`があれば、機能マップ・関連ADR等に加え、図(システム構成図・コンポーネント図・ER図)に影響がないか確認する(外部サービス・使用テーブル・spec間依存が変わる修正では図も同じ変更で更新する)
- ホスティング・CI・外部サービスの追加/変更などインフラ・デプロイ構成に触れる修正では、`docs/architecture/`の該当図(インフラ構成図・デプロイメント図など)も同じ変更で更新する([architecture-workflow](../architecture-workflow/SKILL.md)の「更新ルール」参照)

## 仕様承認の要否

修正の種類によって承認ゲートの扱いが分かれる:

- **仕様そのものを変える場合**(ビジネスルールの変更、スコープ外だった項目への対応など): requirements.mdを更新したら、3点セットが揃うのを待たずに[/pr](../pr/SKILL.md)の「早期仕様PR」の手順でブランチ作成・push・PR作成まで行う。続けてdesign.md/tasks.mdを更新し、同じPRに追加コミットする。3点セットが揃ったらそのPRが仕様承認PRになるので、ユーザーの承認を得てから実装に入る
- **仕様は正しく実装が誤っている場合**(純粋なバグ)や、仕様に影響しない軽微な変更(typo・文言修正): 承認ゲートは不要。そのままStep3へ進む

# Step3 修正(TDD)

`feature/<機能名>`ブランチを切り、まずバグ・問題を再現する失敗テスト(🔴Red)を書いてから修正する。別の機能開発に割り込む形で修正する場合は、ブランチを切り替えず[parallel-work](../parallel-work/SKILL.md)(worktree)で作業ディレクトリを分ける(テストの命名・仕様コメントのルールは[/implementation](../implementation/SKILL.md)を参照)。Step2で洗い出した仕様書・テストコメント・`scripts/spec-coverage-skip.json`の追随も同じ変更の中で行う。Next.js固有の挙動差分にぶつかったら、[/implementation](../implementation/SKILL.md)の[references/nextjs-notes.md](../implementation/references/nextjs-notes.md)を確認・追記する。

`specs/<アプリ名>/architecture.md`を持つアプリで、対象specがリリース済みの場合: ブランチを切った直後に機能マップの該当spec行の状態を「実装中」に更新してコミットする。修正が仕上がったら、修正PRを出す前に同じ行を「リリース済み」に戻してそのPRのコミットに含める([/pr](../pr/SKILL.md)の[references/impl-pr.md](../pr/references/impl-pr.md)・[architecture-workflow](../architecture-workflow/SKILL.md)の「更新タイミング」。状態更新専用の後追いPRは作らない)。いずれのタイミングでも更新後の機能マップ全体(表)をチャットに貼って提示する。

# 完了時の次ステップ案内

**仕様ドキュメントのArtifact発行(必須):** Step2で3点セットを更新した場合は、コミット・pushまで済んだ時点で[spec-artifact](../spec-artifact/SKILL.md)の手順で機能specページのArtifactを同じURLへ更新し、`open`で外部ブラウザに表示したうえでURLを提示する(未発行なら新規発行する)。仕様書に触れていない純粋なバグ修正では不要。実施の可否はユーザーに聞かない(既定動作)。この項は requirement/design/fix/architecture-workflow の4Skillに同趣旨で記載する(変更時は揃って更新する)。

修正・テスト・動作確認が済んだら、[/implementation-review](../implementation-review/SKILL.md)(コードレビュー)→[/pr](../pr/SKILL.md)(実装PR)へ進むことを案内する。動作確認・URL案内の方法は[/implementation](../implementation/SKILL.md)の「動作確認」を参照(画面に変更がある修正では、devサーバーを起動したままアクセスURLをこの案内に明記する)。

この時点の成果物(修正・テスト)はコミット済みのため、ここでcompactや新しいセッションへの切り替えを行っても支障はない。新しいセッションの名称と次のセッションにそのまま貼り付けられるプロンプトを、1行目=名称・2行目=プロンプトの単一のコードブロックとして毎回提示してから終える(名称とプロンプトを分けて提示しない。「セッションを閉じても大丈夫」とだけ述べて済ませない。名称は前のセッションと同じ<機能名>に次工程名を()で添えた形。1行目の例: `<機能名>(コードレビュー)` / 2行目の例: `/implementation-review を実行してください。対象ブランチは feature/<機能名>です。`)。
