> **この表と書式はこのファイルだけに書く。** 書き手(/requirement・/design・/fix)も検査(/spec-review)もこのファイルを見る。手順書側に表を転記しない(転記すると必ずずれる)。手順書に置くのは、この規約に沿ったひな形(コードブロック)だけ。

# 何のための規約か

仕様書が長くなると、承認者が全部読まないまま承認してしまう。細かい`[n]`・手順・表はAIが実装時に読めば足りるのに、承認者と同じ画面に並んでいるため、判断に効く行が埋もれる。

**狙いは「承認者が目を通す量を1specあたり2,500字以内にする」こと。** 情報を削るのではなく、読み手ごとに見せ方を分ける(AI向けの本文は折りたたみの中に全部残す)。

# 1. 見出しごとに読み手を1人だけ決める

| ファイル | 見出し | 読み手 | 本文の見え方 | 要点に書くもの |
|---|---|---|---|---|
| requirements.md | サマリ | 人 | 見える | 誰の何を解決するか、作るものと何のために要るか、進め方 |
| requirements.md | 概要 | 人 | 見える | - |
| requirements.md | ユーザーストーリー | 人 | 見える | - |
| requirements.md | ユースケース図 | 人 | 見える | - |
| requirements.md | 機能要件 | AI | `###`ごとに要点が見える・`[n]`は畳む | 機能の1行概要 |
| requirements.md | ビジネスルール・制約 / 制約条件 | AI | `###`ごとに要点が見える・`[n]`は畳む | ルールの中身を1行で。数値・閾値があれば値を書き、根拠が未確認ならそう明示する |
| requirements.md | 非機能要件 | 人 | 見える(数値だけの短い箇条書きにする) | - |
| requirements.md | 依存関係 | AI | 要点が見える・本文は畳む | 外部依存ごとの実現性(できる / できない / 未確定)。未確定は名指しする |
| requirements.md | UI/UX要件 | AI | 要点が見える・本文は畳む | 画面・操作の決めごとを1行で |
| requirements.md | スコープ外 | 人 | 見える | - |
| design.md | サマリ | 人 | 見える | 処理の全体像と主要図へのリンク |
| design.md | 決定事項 | 人 | 判断に効く行が見える・残りは畳む | - |
| design.md | 処理フロー | AI | `###`ごとに、図がある処理は図だけが見える・要点と手順は畳む。図が無い処理は要点が見える・手順は畳む | 処理の1行概要(図がある処理では畳みの中の先頭に置く) |
| design.md | バリデーション / エラーハンドリング / 関連するファイル(抜粋) / データベース設計 / API設計 / 画面設計 / コンポーネント設計 / 状態管理 / セキュリティ / パフォーマンス / ログ | AI | 要点が見える・本文は畳む | 内容の1行要約 |
| appendix.md | (全体) | AI | 要点なし・畳まない | - |
| tasks.md | 冒頭の件数行 | 人 | 見える | - |
| tasks.md | タスク本体 | AI | タスク名・目的の1行が見える・内容は畳む | 何のための作業かを1行で |

補足:

- 「人は方針だけ読む」のような**両方読みの見出しは作らない**。必ずどちらか一方にする
- 表に無い見出しを足すときは、見出しの直後に`> 読み手: 人`か`> 読み手: AI`の1行を置く
- 図(Mermaid)は読み手に関わらず折りたたみの外に置く。図の直後の説明1行(正となる文章へのリンク。[architecture-workflow](../architecture-workflow/SKILL.md)の「Mermaidの書き方ルール」)も外でよい
- design.mdの処理フローは、このプロジェクトでは図を「作成条件に該当する処理だけ」に描く([/design](../design/SKILL.md)の「Mermaid図の埋め込みルール」)。そのため図が無い`###`では要点1行を外に出す

# 2. 書式

## 要点と畳み

AIが読む見出しは「見出し → 要点1〜2行 → 折りたたんだ本文」の順にする。

```markdown
## 機能要件

### ノートの削除

ノート一覧から1件ずつ削除できるようにする。〔合意〕

<details><summary>詳細を開く</summary>

- [1] 一覧の各ノートに削除ボタンがあること
- [2] 削除に成功した場合、一覧からそのノートが消えること

</details>
```

- `<summary>`の文言は「詳細を開く」に固定する(機械で判定できるようにするため)
- `</summary>`の直後と`</details>`の直前に空行を1行置く。**空行が無いと中のMarkdownが描画されない**
- 畳みの中の`- [n]`は行頭から書く(インデントしない)。`npm run check:spec-coverage`は行頭の`- [n]`を読むため、畳んでもテストとの対応付けはそのまま効く
- 畳みの中に見出し(`##`〜`####`)を置かない。見出しは常に畳みの外に出す
- タイトルと最初の`##`の間に本文を置かない。どの章にも属さない記載を作らない。例外は次の固定行だけ(出所の目印は付けない)
  - requirements.mdの`> ステータス: 仕様確認中(未実装)`(`check:spec-coverage`が`>`付きの形で読むため引用のまま残す)
  - tasks.mdの件数行とTDD宣言文(後述「tasks.md」)

## 出所の目印

承認者が読む行の行末に、`〔合意〕`か`〔提案〕`をちょうど1つ付ける。**承認者が「自分が決めた行」を読み飛ばせるようにするため**で、これが無いと結局全部読むことになる。

- `〔合意〕` — 要件ヒアリング・[/consult](../consult/SKILL.md)・承認時の会話で決めたこと
- `〔提案〕` — 会話に無く、書き手が補ったこと
- **迷ったら`〔提案〕`。** 〔提案〕に寄せる誤りは読む量が増えるだけだが、〔合意〕に寄せる誤りは読まれるべき行が読み飛ばされる
- ひな形の目印は置き場所の例。行ごとに選び直す。**言い換えた要求・補った根拠・書き手が思いついたスコープ外は`〔提案〕`。見えている行が全部`〔合意〕`になったら付け方を疑う**(ひな形をそのまま写すと全行が〔合意〕になる事故が実際に起きた)
- 付ける場所は、人が読む見出しの箇条書き各行の行末と、AIが読む見出しの要点の文末。見出し・図・図の説明1行・畳みの中には付けない。決定事項の表は「出所」列に書く
- [/autopilot](../autopilot/SKILL.md)・designerエージェントの`【推測】`マーカーを付けた行は、出所の目印も`〔提案〕`にする(`【推測】`はマージ前に外すが、`〔提案〕`は残す)
- 承認・マージ後も目印は付け替えない(誰が決めた行かの記録として残す)
- 会話ドリブン原則([/requirement](../requirement/SKILL.md)・[/design](../design/SKILL.md))は変わらない。方針は会話で合意してから書く。`〔提案〕`は、方針の範囲内で書き手が補った言い回し・根拠・派生した項目を、承認時に確かめてもらうための目印

## 決定事項の表

design.mdの「サマリ」の直後に`## 決定事項`を置く。**承認者が最初に読むのはここ。**

```markdown
## 決定事項

| 論点 | 選んだ案 | 採らなかった案 | 理由 | 影響範囲 | 出所 |
|---|---|---|---|---|---|
| 付箋の保存先 | Supabaseの専用テーブル | ブラウザのlocalStorage | 端末をまたいで見返せるようにするため | データベース設計・セキュリティ | 〔合意〕 |

<details><summary>詳細を開く</summary>

| 論点 | 選んだ案 | 採らなかった案 | 理由 | 影響範囲 | 出所 |
|---|---|---|---|---|---|
| (判断への影響が小さいもの) | | | | | 〔提案〕 |

</details>
```

- design.mdの本文で選んだ案・却下した案は、すべてこの表のどちらかに載せる(本文にだけある選択を作らない)
- 判断に効く行だけを外に見せ、残りは同じ見出しの折りたたみの中に2つ目の表として残す(捨てない)
- 「理由」は1〜2行に収める。長い経緯はADRへ分ける(置き場は[/requirement](../requirement/SKILL.md)の「最新仕様のみを書く」参照)
- 表の各行は`check:spec-coverage`で「決定事項 > <論点>」という項目になる。テスト対象の振る舞いではないため、既存の表(データベース設計など)と同様に`scripts/spec-coverage-skip.json`へ理由付きで登録する

## 付録の分離

設定ファイル・キャッシュ・コマンド・ログの**書式**はdesign.mdの本文に置かず、同じspecフォルダの`appendix.md`に移してリンクを1行残す。appendix.mdには書式だけを置き、処理の手順・分岐・方針は置かない(手順はdesign.mdが正)。付録に回す内容が無い機能ではappendix.mdを作らない。

## tasks.md

- タイトルの直下に件数行とTDD宣言文をこの順に置く(どちらも引用`>`の1行)
  - 件数行: `> 全<N>件(Task 1〜Task <N>)`。**Nはタスクの通し番号のいちばん下を写すだけにする**(数え上げない。数え上げさせると実際のタスク数と合わない事故が続いた)
  - TDD宣言文: [/design](../design/SKILL.md)の「tasks.mdの書き方」の一文
- 各タスクは「タスク名の行 → 目的1行 → 折りたたんだ内容(🔴/🟢の手順・対象ファイル)」の順にする。ひな形は[/design](../design/SKILL.md)

# 3. 提出前の読み返し(これが一番効く)

書いた本人は自分の文脈で読めてしまうため、**主語の抜け・目的の書かれていない成果物・意味の取れない略称は、書き手には見えない。** 折りたたみの外に見えている行だけを抜き出して読み、次を確かめてから出す。

1. 抜き出す(`<details>`〜`</details>`とMermaidのコードを除いた行):
   ```bash
   f=specs/<アプリ名>/<機能名>
   awk '/^<details>/{d=1} /^```mermaid/{m=1} !d&&!m{print} /^<\/details>/{d=0} m&&/^```$/{m=0}' $f/requirements.md $f/design.md
   ```
   同じコマンドの末尾に`| tr -d '[:space:]' | wc -m`を付けると、見えている文字数(空白を除く)が出る。文字数は目で数えず、このコマンドの結果を使う
2. 抜き出した行だけで次を確かめる
   - その行だけで意味が取れるか。主語(何が)と対象(何を・どのファイルを)が省かれていないか
   - この仕様で作るものについて、何のために作り何が入っているかが初出で書かれているか。名前だけ出て目的が無いものは無いか
   - 用語の説明を前段に並べていないか(読んでそのまま分かる文にする)
   - 目印が全部`〔合意〕`になっていないか
   - タスク名だけで何をするか分かるか(tasks.mdも同じ要領で見出し・タスク名・目的の行を読む)
3. **抜き出した行をそのまま完了報告に貼る。** 承認者がファイルを開かなくても、読む量の全部をその場で確認できる状態にする

# 4. 完了条件

新しく書いたspecは、次をすべて満たしてから完了報告・仕様承認PRに進む。

- requirements.md + design.mdの、折りたたみの外に見えている文字数の合計が**2,500字以内**(上記コマンドで測る)
- 承認者が読む行すべてに`〔合意〕` / `〔提案〕`がちょうど1つ付いている
- design.mdに決定事項の表があり、本文の選択・却下がそこに載っている
- 上記「提出前の読み返し」の抜き出しを完了報告に貼った

# 5. 既存specの移行

- 既存の仕様書は一括で書き換えない
- 次にそのspecへ手を入れる工程([/fix](../fix/SKILL.md)のStep2など)で、同じ変更のついでに新形式へ直す。**requirements.mdとdesign.mdの片方だけ直した状態で残さない**(tasks.mdは追記するタスクから新形式にすればよい)
- 移行したspecの2,500字は目安とし、超える場合は完了報告に文字数と超えた理由を一言書く
- 新形式に直していない既存specは、[/spec-review](../spec-review/SKILL.md)でこの規約の違反として扱わない(今回手を入れたspecだけが対象)

# 規約を変えるとき

実装や方針を変えたら、それを説明している文を全部開いて読み直す。1か所直しても、同じ条件を説明する文が仕様書・付録・手順書に散っていて、古い世代が残る事故が繰り返し起きた。判定名(`〔提案〕`・`詳細を開く`・`決定事項`・`spec-layout`など)で`.claude/`・`docs/`・`specs/`を横断検索して全部そろえる。

機械検査(畳み忘れ・要点の長さ超過・目印の漏れなどを字句で判定するスクリプト)は未導入。目視でも運用できるが、目印の漏れと畳み忘れは目視では確実に取りこぼすため、運用が定着したら`scripts/`への追加を検討する。
