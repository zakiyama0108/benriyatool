> ワークフロー上の位置: **/consult(本Skill・任意)** → [/requirement](../requirement/SKILL.md) または [/fix](../fix/SKILL.md)

> **次フェーズのモデル:** 相談内容の複雑度に基づいて選ぶ
> - 複雑な方針判断・技術選定・影響範囲の分析が必要: **Opus** (論点の整理・トレードオフの分析に高い推論能力が必要)
> - 標準的な相談(機能の切り方・既存機能への影響判定): **Sonnet**
> - 軽微な相談(簡単な質問・確認): **Sonnet**

# 共通の前提

- どのアプリでも、基本無料でサービスを立ち上げる案を優先的に検討する。有料化・課金モデルは、無料での実現が難しい明確な理由がある場合にのみ選択肢として挙げる

# 壁打ちの進め方

- このSkillの間はコード・仕様書・設定ファイルを一切変更しない(読むのは自由)。結論が出て、ユーザーが次のステップへ進むと明言してから着手する
- 前提を確認する質問から始め、論点を1つずつ潰す。複数の選択肢がある場合はトレードオフと推奨案をセットで示す(選択肢の羅列だけで終えない)
- 判断材料は推測ではなくリポジトリの実物(`specs/`・`app/`・`docs/adr/`・`specs/<アプリ名>/architecture.md`)を読んで揃える
- ただし**読むのは相談テーマが確定してから**、その論点に必要な範囲だけにする。テーマを聞く前にgit statusや未コミットの変更から話題を推測して先読みしない(読む対象の選定こそ推測になってはいけない。テーマが1行で済む相談まで読み込みが走ると無駄なトークンを使う)

# 会話ドリブンの起点(後工程ドキュメントの素になる)

この壁打ちで合意・提案した方針(技術選定・機能の切り方・画面イメージ・非機能の勘所など)は、後工程の requirements.md / design.md / architecture.md にそのまま記載される「素」になる。これらのドキュメントに書く方針は、任意項目も含め会話の中で確認または提案・合意したものだけを書く運用([/requirement](../requirement/SKILL.md)・[/design](../design/SKILL.md)・[architecture-workflow](../architecture-workflow/SKILL.md)の「会話ドリブン原則」)なので、ここで曖昧なまま次工程に渡さない。決めたこと・こちらから提案したこと・保留にしたことを明示して締める(保留はrequirement/designの会話で改めて詰める前提で引き継ぐ)。

# 議論の出口

結論が出たら、内容に応じて次のステップを案内する:

- 新しい機能・アプリを作ることになった → [/requirement](../requirement/SKILL.md) へ
- 既存機能の修正・バグ対応になった → [/fix](../fix/SKILL.md) へ
- 複数アプリにまたがる技術選定が決まった → `docs/adr/` にADRを残すことを提案する
- アプリ内の構成方針が決まった → `specs/<アプリ名>/architecture.md` への反映を提案する([architecture-workflow](../architecture-workflow/SKILL.md)参照)
