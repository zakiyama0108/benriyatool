> ワークフロー上の位置: 遷移図1(新機能開発)全体を貫く**モードSkill**。各工程の手順はすべて既存の工程Skillに従い、本Skillは「どこで止まり、どこを自走するか」だけを定める(手順の二重メンテをしない)

ユーザーと止まって対話するのは次の**2箇所だけ**。それ以外は完了報告まで自走し、実装PRのマージも自動で行う。

1. [/requirement](../requirement/SKILL.md)の要件ヒアリング(設計の分かれ道になる事項の確認もここに含める。下記「ヒアリングの範囲」)
2. 仕様承認PRでの一括レビュー(複数回のやりとり可)

# 前提条件

- **小規模・低リスクの機能にだけ使う。** 金額計算などビジネスルールが複雑な機能、個人情報の扱いが変わる機能、影響範囲の読めない変更には使わない(通常フローで工程ごとに確認する)。対象として適切か迷ったら、自走を始める前にユーザーに確認する
- 新機能([/requirement](../requirement/SKILL.md)起点)のみ対象。バグ修正([/fix](../fix/SKILL.md)起点)の自動運転は現時点ではスコープ外
- **推奨モデル: Sonnet。** メインスレッドのモデルはフロー途中で自動では切り替えられず、既存Skillの「次フェーズのモデル」運用(工程ごとに人が切り替える)がこのモードでは使えない。対象が小規模である前提なので、発動時(遅くとも自動運転宣言の時点)に`/model`でSonnetへ切り替えることを案内する。以降のメインスレッド全工程と、inherit設定のAgent(spec-reviewer / code-reviewer)がこのモデルで走る

# フロー

各ステップの手順・テンプレートはリンク先の工程Skillに従う。

1. **要件定義(対話①)**: [/requirement](../requirement/SKILL.md)をそのまま実施する(着手前チェック・ヒアリングも通常どおり)。ヒアリングは要件に閉じず、設計の分かれ道になる事項もここで合わせて確認する(下記「ヒアリングの範囲」)
2. **自動運転宣言**: ヒアリング完了後、「ここから仕様承認PRの提示まで自走する」と宣言し、以降はユーザー確認なしで進む
3. **設計**: [/design](../design/SKILL.md)でdesign.md・tasks.mdを作成する。ヒアリングで確認できていない細部は質問せず妥当な推測で補い、推測で決めた箇所には推測マーカーを付ける(下記)
4. **仕様レビュー**: [/spec-review](../spec-review/SKILL.md)(spec-reviewerエージェント)。🔴/🟡は[/resolve](../resolve/SKILL.md)で自動対応し再レビューする。ただし対応に要件・ビジネスルールの変更が必要な指摘は例外停止(下記)
5. **仕様承認PR(対話②)**: [/pr](../pr/SKILL.md)で仕様承認PRを作成する。PR本文の「判断に迷った点・レビューしてほしい点」に**推測箇所の一覧**を明記し、ユーザーに一括レビューを依頼する。指摘はセッション上・PRコメント(`gh pr view <PR番号> --comments`で取得)のどちらで受けてもよく、[/resolve](../resolve/SKILL.md)で修正して再提示する(何往復してもよい)
6. **承認処理**: ユーザーの明示的なOKを得たら、残っている推測マーカーを全て削除するコミットをpushし、CI成功を待って自動マージする(下記「自動マージ」)
7. **実装**: マージ後、新しいfeatureブランチを切り([/pr](../pr/SKILL.md)共通ルール)、[/implementation](../implementation/SKILL.md)を**implementerエージェントに常に委譲**する(メインスレッドは進行管理に徹し、code-reviewerの「別コンテキストの新鮮な目」を効かせる)
8. **実装レビュー**: [/implementation-review](../implementation-review/SKILL.md)(code-reviewerエージェント)。🔴/🟡は[/resolve](../resolve/SKILL.md)で自動対応し再レビューする。仕様の変更が必要な指摘は例外停止
9. **実装PR**: [/pr](../pr/SKILL.md)(impl-pr-reviewerチェック→PR作成)。CI成功を待って自動マージする
10. **リリース確認**: [/release-check](../release-check/SKILL.md)(release-checkerエージェント)
11. **完了報告**: 全工程のサマリをまとめて報告する — 作成したspec、PRのURL2件、テスト件数、本番スモークチェック結果、自動対応したレビュー指摘の一覧、例外停止の有無

# ヒアリングの範囲

対話①では/requirementの要件ヒアリングに加えて、**設計(design.md)の分かれ道になる事項**も先に確認する。ここで聞いておくほど推測マーカーが減り、仕様承認PRでの一括レビューが軽くなる。

- **聞くもの**(設計への影響が大きい事項):
  - 分岐パターンが多く、どのパターンを扱うかで処理フローが大きく変わる事項
  - パターンの切り替えによって提供する機能・画面が大きく変わる事項
  - 誤った推測のまま進むと手戻りが大きい事項(データの保存有無・既存機能への影響範囲など)
- **聞かないもの**(推測で進めてマーカーを付ける): 画面の文言・表示順・エラー時の扱いなど、PRレビューで軽く直せる細部
- 聞き方は/requirementのヒアリングと同じく一度に全部聞かず重要な順に。確認した内容は要件ならrequirements.mdへ、設計判断ならdesign.mdへ反映する(確認済みなのでマーカーは付けない)

# 推測マーカー

- **対象**: ヒアリングで確認していないのに設計判断として決めた事項(画面の文言・表示順・エラー時の扱い・スコープの線引きなど)。design.mdだけでなく、requirements.mdに要件として書き足す場合も同様
- **書き方**: その箇条書き・文の末尾に `【推測】` を付ける
- **削除**: 仕様承認PRでユーザーのOKが出たら、マージ前に全マーカーを削除する(`grep -r '【推測】' specs/` で残りゼロを確認してからマージする)。レビュー往復の中でユーザーが確認・修正した箇所は、その時点でマーカーを外してよい

# 自動マージ(通常ルールの例外)

「mainへのマージはユーザーがGitHub UIで行う」([/pr](../pr/SKILL.md)共通ルール)の例外は本モードのみ。条件を満たさない限りマージしない。

- **仕様承認PR**: ユーザーの明示的なOK(セッションでの発言またはPRのApprove)+推測マーカー残りゼロが条件。OKなしで勝手にマージしない
- **実装PR**: [/implementation-review](../implementation-review/SKILL.md)が🟢のみ+impl-pr-reviewerの❌なしが条件(仕様はマージ済みの承認仕様が根拠なので、ここでの追加確認は求めない)
- **手順**: リポジトリのauto-merge設定は無効のため、`gh pr checks <PR番号> --watch`でCI(test)の完了を待ち、成功したら`gh pr merge <PR番号> --squash`でマージする(マージ方式は既存履歴に合わせてsquash)。branch protectionがstrict(mainへの追随必須)のため、mainが先行していてマージできない場合は`gh pr update-branch <PR番号>`で追随し、CIを待ち直す
- CIが失敗した場合は原因の修正を1回だけ自動で試み、それでも失敗するなら例外停止する

# 例外停止

次のいずれかに当たったら自走をやめ、状況と選択肢をまとめて報告してユーザーの指示を待つ(勝手に要件・仕様を書き換えて進まない)。正常系では発動しない安全弁であり、対話ポイントを増やすものではない。

- 要件・仕様どおりに実装できない事情が判明した(implementerの中断報告、仕様の矛盾・不足の発見を含む)
- レビュー指摘への対応が要件・ビジネスルールの変更を要する
- 着手前チェックで同じspecを扱う既存PR・進行中ブランチを検知した
- CI・デプロイの失敗が自動対応(1回)で解消しない
- [/release-check](../release-check/SKILL.md)が本番の問題を報告した(/fixへの合流はユーザー判断)

# 完了時の次ステップ案内

完了報告をもって終了。本番で問題が見つかった場合は[/fix](../fix/SKILL.md)へ(自動運転はここまで。修正は通常フローで行う)。
