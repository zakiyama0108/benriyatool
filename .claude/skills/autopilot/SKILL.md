> ワークフロー上の位置: 遷移図1(新機能開発)・遷移図2(バグ修正・既存機能改修)全体を貫く**モードSkill**。各工程の手順はすべて既存の工程Skillに従い、本Skillは「どこで止まり、どこを自走するか」だけを定める(手順の二重メンテをしない)

対話ポイントは起点によって異なる。それ以外は完了報告まで自走し、実装PRのマージも自動で行う。

- **新機能起点**([/requirement](../requirement/SKILL.md)から): 次の**2箇所**(UI(画面)に変更がある場合は**3箇所**)
  1. [/requirement](../requirement/SKILL.md)の要件ヒアリング(設計の分かれ道になる事項の確認もここに含める。下記「ヒアリングの範囲」)
  2. 仕様承認PRでの一括レビュー(複数回のやりとり可)
  3. (UIに変更がある場合のみ)実装レビュー通過後・実装PR自動マージ前の画面レビュー(localhostのアクセスURLを提示し、実際の見た目をユーザー自身に確認してもらう。複数回のやりとり可。下記「フロー(新機能起点)」ステップ9)
- **バグ修正・既存機能改修起点**([/fix](../fix/SKILL.md)から): [/fix](../fix/SKILL.md)のStep2で仕様変更が必要と判定された場合のみ新機能起点と同じ入口確認・仕様承認PRレビューの2箇所が加わる。UIに変更がある場合は、仕様変更の有無にかかわらずさらに1箇所(実装レビュー通過後の画面レビュー、上記3.と同じ運用)が加わる。仕様変更・UI変更のいずれも伴わない純粋なバグ・軽微な変更は**対話なしで完走することがある**(下記「フロー(fix起点)」)

# UI確認の優先(仕様承認PRの例外)

対象の変更がUI(画面)に見える形の変更であり、localhostで実際の見た目を確認できる場合、仕様承認PRでの一括レビュー(対話②。新機能起点ステップ5、fix起点ステップ3)はテキストによる仕様説明だけで判断を求めない。可能な範囲で対象箇所を先に実装し、devサーバーを起動してlocalhostのアクセスURLを提示したうえでレビューを依頼する(通常のfix/requirementフローが定める「承認までコードは書かない」原則の、本モード・UI変更時のみの例外)。**ユーザーに指示される前に、実装が終わった時点でこちらから提示する**(承認を求める・完了を報告する等どのタイミングであっても、UI変更が絡む限りは省略しない)。

- **提示するのは生きたURLそのもの。** ui-checkerエージェントへの委譲(スクリーンショットを撮って報告するだけの確認)で代替しない。ui-checkerはメインスレッド自身が動作を検証してテキストで報告する用途のものであり、ユーザー自身がブラウザで開いて確認する対話②・対話③の代わりにはならない
- devサーバーはユーザーが確認を終えたと明言するまで、または次の作業で明示的に停止が必要になるまで起動したままにする(確認前に停止しない)
- 実装済みの見た目がすでにレビュー材料になるため、後続の画面レビュー(対話③)は重複確認を避け、実装レビュー通過後の最終確認のみに絞ってよい
- UIに見える変化を伴わない設計判断(データの保存方針など)はこれまで通りテキストでのレビュー依頼でよい

# 前提条件

- **小規模・低リスクの変更にだけ使う。** 金額計算などビジネスルールが複雑な機能・修正、個人情報の扱いが変わる変更、影響範囲の読めない変更には使わない(通常フローで工程ごとに確認する)。対象として適切か迷ったら、自走を始める前にユーザーに確認する
- **対象範囲**: 新機能([/requirement](../requirement/SKILL.md)起点)、または小規模なバグ修正・既存機能改修([/fix](../fix/SKILL.md)起点)。[/fix](../fix/SKILL.md)のStep1で「新規spec作成が必要」と判定された場合は、以降「フロー(新機能起点)」に合流する(要件ヒアリングを対話①として行う)
- **推奨モデル: Sonnet。** メインスレッドのモデルはフロー途中で自動では切り替えられず、既存Skillの「次フェーズのモデル」運用(工程ごとに人が切り替える)がこのモードでは使えない。対象が小規模である前提なので、発動時(遅くとも自動運転宣言の時点)に`/model`でSonnetへ切り替えることを案内する。以降のメインスレッド全工程と、inherit設定のAgent(spec-reviewer / code-reviewer)がこのモデルで走る

# フロー(新機能起点)

各ステップの手順・テンプレートはリンク先の工程Skillに従う。

1. **要件定義(対話①)**: [/requirement](../requirement/SKILL.md)をそのまま実施する(着手前チェック・ヒアリングも通常どおり)。ヒアリングは要件に閉じず、設計の分かれ道になる事項もここで合わせて確認する(下記「ヒアリングの範囲」)
2. **自動運転宣言**: ヒアリング完了後、「ここから仕様承認PRの提示まで自走する」と宣言し、以降はユーザー確認なしで進む
3. **設計**: [/design](../design/SKILL.md)を**designerエージェントに常に委譲**してdesign.md・tasks.mdを作成する。ヒアリングで確認できていない細部は質問せず妥当な推測で補い、推測で決めた箇所には推測マーカーを付けるよう起動時に指示する(下記「推測マーカー」)。designerは対象ブランチへのコミット・pushまで完了させるため、メインスレッドは書いたファイル・推測箇所の報告を受け取る
4. **仕様レビュー**: [/spec-review](../spec-review/SKILL.md)(spec-reviewerエージェント)。🔴/🟡は[/resolve](../resolve/SKILL.md)を**resolverエージェントに常に委譲**して対応し再レビューする。ただし対応に要件・ビジネスルールの変更が必要な指摘は例外停止(下記)
5. **仕様承認PR(対話②)**: [/pr](../pr/SKILL.md)で仕様承認PRを作成する。PR本文の「判断に迷った点・レビューしてほしい点」に**推測箇所の一覧**を明記し、ユーザーに一括レビューを依頼する。指摘はセッション上・PRコメント(`gh pr view <PR番号> --comments`で取得)のどちらで受けてもよく、[/resolve](../resolve/SKILL.md)で修正して再提示する(何往復してもよい)
6. **承認処理**: ユーザーの明示的なOKを得たら、残っている推測マーカーを全て削除するコミットをpushし、CI成功を待って自動マージする(下記「自動マージ」)
7. **実装**: マージ後、新しいfeatureブランチを切り([/pr](../pr/SKILL.md)共通ルール)、[/implementation](../implementation/SKILL.md)を**implementerエージェントに常に委譲**する(メインスレッドは進行管理に徹し、code-reviewerの「別コンテキストの新鮮な目」を効かせる)
8. **実装レビュー**: [/implementation-review](../implementation-review/SKILL.md)(code-reviewerエージェント)。🔴/🟡は[/resolve](../resolve/SKILL.md)を**resolverエージェントに常に委譲**して対応し再レビューする。仕様の変更が必要な指摘は例外停止
9. **画面レビュー(対話③、UIに変更がある場合のみ)**: 実装レビューが🟢になったら、UI(画面)に変更があるかを[/implementation](../implementation/SKILL.md)の「動作確認」と同じ基準(バックエンドのみの変更かどうか)で判定する。UIに変更がない場合はこのステップをスキップして次へ進む。UIに変更がある場合は、devサーバーを起動したまま(停止していれば再起動して)アクセスURLを提示し、実際の見た目をユーザー自身にブラウザで確認してもらう。修正依頼が出た場合は[/resolve](../resolve/SKILL.md)を**resolverエージェントに常に委譲**して対応し、再度URLを提示して確認を得る(何往復してもよい)。ユーザーの明示的なOKが出るまで次のステップに進まない
10. **実装PR**: [/pr](../pr/SKILL.md)(impl-pr-reviewerチェック→PR作成)。CI成功を待って自動マージする(UIに変更がある場合は画面レビューのOKも条件。下記「自動マージ」)
11. **リリース確認**: [/release-check](../release-check/SKILL.md)(release-checkerエージェント)
12. **完了報告**: 全工程のサマリをまとめて報告する — 作成したspec、PRのURL2件、テスト件数、本番スモークチェック結果、自動対応したレビュー指摘の一覧、画面レビューの結果(UIに変更があった場合)、例外停止の有無

# ヒアリングの範囲

対話①では/requirementの要件ヒアリングに加えて、**設計(design.md)の分かれ道になる事項**も先に確認する。ここで聞いておくほど推測マーカーが減り、仕様承認PRでの一括レビューが軽くなる。

- **聞くもの**(設計への影響が大きい事項):
  - 分岐パターンが多く、どのパターンを扱うかで処理フローが大きく変わる事項
  - パターンの切り替えによって提供する機能・画面が大きく変わる事項(新しい画面が増える場合は[/requirementの要件ヒアリング](../requirement/SKILL.md#要件ヒアリング)の画面イメージ提示ルールに従い、案を複数提示してから選んでもらう)
  - 誤った推測のまま進むと手戻りが大きい事項(データの保存有無・既存機能への影響範囲など)
- **聞かないもの**(推測で進めてマーカーを付ける): 画面の文言・表示順・エラー時の扱いなど、PRレビューで軽く直せる細部
- 聞き方は[/requirementの要件ヒアリング](../requirement/SKILL.md#要件ヒアリング)と同じく一度に全部聞かず重要な順に、回答を受けたら残りが埋まっているか確認して往復する。**今回の機能に「聞くもの」に該当する事項がある限り、それらが確認できるまでStep2(自動運転宣言)に進まない**(見切り発車で自走を始めない)。確認した内容は要件ならrequirements.mdへ、設計判断ならdesign.mdへ反映する(確認済みなのでマーカーは付けない)

# フロー(fix起点)

各ステップの手順・テンプレートはリンク先の工程Skillに従う。新機能起点との違いは、design.md/tasks.mdを作る独立した設計工程がなく、[/fix](../fix/SKILL.md)のStep2(3点セットへの影響洗い出し)がその役割を兼ねる点。

1. **入口確認・影響洗い出し(対話①)**: [/fix](../fix/SKILL.md)のStep1(新規spec vs 既存spec更新の判定。着手前チェックを含む)・Step2(3点セットへの影響洗い出し・承認要否判定)を実施する。ユーザーの依頼内容だけで判断できない曖昧な点(再現条件・期待する挙動の絞り込みなど)があればここで確認する。判断できる場合は対話なしで次に進めてよい。Step1で新規spec相当と判定した場合は「フロー(新機能起点)」の対話①(要件ヒアリング)に合流する
2. **自動運転宣言**: Step2完了後、「ここから自走する」と宣言し、以降はユーザー確認なしで進む
3. **分岐(仕様承認ゲート)**:
   - **仕様変更あり**(ビジネスルール変更・スコープ外だった項目への対応など): [/pr](../pr/SKILL.md)の早期仕様PRの手順でrequirements.md更新分をpush・PR作成する。続けてdesign.md/tasks.mdの更新を追加コミットする。PR本文の「判断に迷った点・レビューしてほしい点」に**推測箇所の一覧**を明記し、ユーザーに一括レビューを依頼する(**対話②**、新機能起点の仕様承認PRと同じ運用)。ユーザーの明示的なOK+推測マーカー残りゼロを得たら自動マージする(下記「自動マージ」の仕様承認PR条件を準用)
   - **仕様変更なし**(純粋なバグ・軽微な変更): 対話②は発生させず、そのまま次のステップへ進む
4. **TDD修正**: [/fix](../fix/SKILL.md) Step3(再現テスト→修正)を**implementerエージェントに常に委譲**する。ヒアリングで確認できていない実装上の判断(文言・表示上の数値など)は質問せず妥当な推測で補ってよいが、合理的な選択肢が複数あり自信を持って決められない場合は中断して報告するよう起動時に指示する
5. **実装レビュー**: [/implementation-review](../implementation-review/SKILL.md)(code-reviewerエージェント)。🔴/🟡は[/resolve](../resolve/SKILL.md)を**resolverエージェントに常に委譲**して対応し再レビューする。仕様の変更が必要な指摘は例外停止
6. **画面レビュー(対話③、UIに変更がある場合のみ)**: 実装レビューが🟢になったら、UI(画面)に変更があるかを[/implementation](../implementation/SKILL.md)の「動作確認」と同じ基準で判定する。UIに変更がない場合はこのステップをスキップして次へ進む。UIに変更がある場合は、devサーバーを起動したまま(停止していれば再起動して)アクセスURLを提示し、実際の見た目をユーザー自身にブラウザで確認してもらう。修正依頼が出た場合は[/resolve](../resolve/SKILL.md)を**resolverエージェントに常に委譲**して対応し、再度URLを提示して確認を得る(何往復してもよい)。ユーザーの明示的なOKが出るまで次のステップに進まない
7. **実装PR**: [/pr](../pr/SKILL.md)(impl-pr-reviewerチェック→PR作成)。ステップ4で確認なしに決めた判断があれば、PR本文の「判断に迷った点」に明記する。CI成功を待って自動マージする(下記「自動マージ」の実装PR条件と同じ。UIに変更がある場合は画面レビューのOKも条件)
8. **リリース確認**: [/release-check](../release-check/SKILL.md)(release-checkerエージェント)
9. **完了報告**: 全工程のサマリをまとめて報告する — 修正内容、PRのURL(仕様変更ありの場合2件・なしの場合1件)、テスト件数、本番スモークチェック結果、自動対応したレビュー指摘の一覧、画面レビューの結果(UIに変更があった場合)、確認なしで決めた判断点の一覧、例外停止の有無

# 推測マーカー

- **対象**: ヒアリング・入口確認で確認していないのに設計判断(fix起点では実装判断を含む)として決めた事項(画面の文言・表示順・エラー時の扱い・スコープの線引きなど)。design.mdだけでなく、requirements.mdに要件として書き足す場合も同様。fix起点で仕様変更を伴わない場合はrequirements.md/design.mdへの書き足しがないため、実装PR本文の「判断に迷った点」への記載で代替する(上記「フロー(fix起点)」ステップ7)
- **書き方**: その箇条書き・文の末尾に `【推測】` を付ける
- **削除**: 仕様承認PRでユーザーのOKが出たら、マージ前に全マーカーを削除する(`grep -r '【推測】' specs/` で残りゼロを確認してからマージする)。レビュー往復の中でユーザーが確認・修正した箇所は、その時点でマーカーを外してよい

# 自動マージ(通常ルールの例外)

「mainへのマージはユーザーがGitHub UIで行う」([/pr](../pr/SKILL.md)共通ルール)の例外は本モードのみ。条件を満たさない限りマージしない。

- **仕様承認PR**: ユーザーの明示的なOK(セッションでの発言またはPRのApprove)+推測マーカー残りゼロが条件。OKなしで勝手にマージしない
- **実装PR**: [/implementation-review](../implementation-review/SKILL.md)が🟢のみ+impl-pr-reviewerの❌なしが条件(仕様はマージ済みの承認仕様が根拠なので、ここでの追加確認は求めない)。UI(画面)に変更がある場合はさらに、画面レビュー(上記フロー内のステップ)でのユーザーの明示的なOKも条件
- **手順**: リポジトリのauto-merge設定は無効のため、`gh pr checks <PR番号> --watch`でCI(test)の完了を待ち、成功したら`gh pr merge <PR番号> --squash`でマージする(マージ方式は既存履歴に合わせてsquash)。branch protectionがstrict(mainへの追随必須)のため、mainが先行していてマージできない場合は`gh pr update-branch <PR番号>`で追随し、CIを待ち直す
- CIが失敗した場合は原因の修正を1回だけ自動で試み、それでも失敗するなら例外停止する

# 例外停止

次のいずれかに当たったら自走をやめ、状況と選択肢をまとめて報告してユーザーの指示を待つ(勝手に要件・仕様を書き換えて進まない)。正常系では発動しない安全弁であり、対話ポイントを増やすものではない。

- 要件・仕様どおりに実装できない事情が判明した(implementerの中断報告、仕様の矛盾・不足の発見を含む)
- レビュー指摘への対応が要件・ビジネスルールの変更を要する
- 着手前チェックで同じspecを扱う既存PR・進行中ブランチを検知した
- CI・デプロイの失敗が自動対応(1回)で解消しない
- [/release-check](../release-check/SKILL.md)が本番の問題を報告した(/fixへの合流はユーザー判断)
- (fix起点)実装上の判断に合理的な選択肢が複数あり、確信を持って決められない

# 完了時の次ステップ案内

完了報告をもって終了。本番で問題が見つかった場合は[/fix](../fix/SKILL.md)へ(自動運転はここまで。修正は通常フローで行う)。
