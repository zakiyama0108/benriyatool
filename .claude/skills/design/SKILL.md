# 前提条件

- **着手前チェック(重複作業の防止):** `git fetch origin main` でローカルmainの遅れを確認し、遅れていれば先に最新化する。続けて `gh pr list --state all --limit 20 --search "<対象のアプリ名や機能名>"` と `git ls-remote --heads origin` で、同じspec・同じ機能を扱う既存PR・進行中ブランチがないか確認する。該当しそうなブランチ/PRが複数見つかった場合は、PR本文・ブランチ名を`specs/<アプリ名>/<機能名>/`のパスで絞り込む。それでも複数残る、またはどれが自分の続きか判断できない場合は、推測でどれかを選ばず候補一覧をユーザーに提示して確認する。1件に絞れた場合、それが「自分がこれから進める工程の一つ前の工程が作ったもの」(例: /requirementが作った`feature/<機能名>`ブランチに/designで続きを積む場合)であればそれは重複ではないので、そのブランチをcheckoutして続行する。それ以外(既に先の工程まで進んでいる、または別セッション・別人の作業)は作業を始めずユーザーに報告する(この項は requirement/design/fix/implementation の4Skillに同文で記載。変更時は揃って更新する)
- 対象の`specs/<アプリ名>/<機能名>/requirements.md`が存在すること。[/requirement](../requirement/SKILL.md)が作った早期仕様PR・`feature/<機能名>`ブランチがある場合はそのブランチをcheckoutして確認する(まだmainにマージされていないため、mainだけを見ても見つからない)。ブランチ自体がなければ[/requirement](../requirement/SKILL.md)(要件定義)から始める(要件ヒアリングを飛ばして設計に入らない)

# 実施方法(メインスレッド or designerエージェント)

通常はメインスレッドが本Skillの手順で直接設計する(要件定義時の議論の文脈を引き継げるため)。次の場合はdesignerエージェント(`.claude/agents/designer.md`)に設計を委譲できる(役割分担の背景は[docs/adr/0002](../../../docs/adr/0002-skill-agent-separation.md)を参照):

- [parallel-work](../parallel-work/SKILL.md)で複数機能を並行開発していて、一方の設計を任せたいとき

委譲する場合は対象のrequirements.mdと作業するfeatureブランチ(またはworktree)を伝え、`isolation: "worktree"`で起動する。エージェントは要件定義に立ち返るべき不明点に気づくと作業を中断して報告を返すので、ユーザーに確認してから再開する。エージェントは対象ブランチへのコミット・pushまで完了させるため、メインスレッドは書いたファイル・(推測マーカーを付けた場合は)その箇所の短い報告を受け取るだけでよい。

# UIデザインの確定(Step0・画面を伴う機能のみ)

新しい画面・大きく見た目が変わる画面がある機能では、処理フロー中心のdesign.md作成に入る前に、まずビジュアルなUIデザインを確定する。[/requirementの要件ヒアリング](../requirement/SKILL.md#要件ヒアリング)で作ったラフなワイヤーフレーム(ASCII)は「画面に何があるか」の合意にとどまるため、ここでは実際の見た目(レイアウト・配色・コンポーネント・レスポンシブ・アクセシビリティ)まで踏み込んで決める。既存画面への軽微な変更(文言・配置の微調整)ではこのステップを飛ばし、通常のdesign.md作成に進んでよい。

1. メインスレッドがユーザーにヒアリングする(どんな雰囲気にしたいか・参考にしたいデザイン・優先したい情報など)。ヒアリング内容と対象requirements.mdを渡し、ui-designerエージェント(`.claude/agents/ui-designer.md`)に複数のデザイン候補(狙い・トレードオフ・v0向けプロンプト)を作成させる
2. 候補をユーザーに提示し、AskUserQuestionのpreview機能などで選んでもらう。気に入ったものがなければヒアリングに戻り、ui-designerに再度候補を作らせる
3. 候補が決まったら、実際にv0(https://v0.app等)にそのプロンプトを渡し、生成されたコードをユーザーと一緒に確認する。修正したい点があればヒアリング→再生成を繰り返す
4. ユーザーの承認が得られたら、採用したデザイン候補の概要とv0生成コードへの参照を後述「design.mdの書き方」の7. 画面設計に反映し、通常のdesign.md/tasks.md作成に進む。tasks.mdの最初のタスクには「v0生成コードの取り込み・整形(ui-integratorへの委譲可)」を追加する(詳細は[/implementation](../implementation/SKILL.md#ui統合タスクv0生成コードの取り込み)参照)

# design.mdの書き方

requirements.mdのビジネスルールを「どんな手順・分岐で処理するか」を日本語の文章(変数名・数式なし)で書く**処理フロー**を中心に、この機能が実際に関わるファイル・DB・画面などを確認用に書き足す。フォルダ構成の一般ルールや、プロジェクト全体の非機能要件・設計方針はCLAUDE.md/requirements.mdの領分のためここには書かない。分岐・複数ステップのロジックが1つもない機能(例: 純粋なルーティング変更)は、design.md自体を作らずrequirements.mdのみで完結してよい。

以下の見出しのうち**処理フロー・エラーハンドリング・関連するファイル(抜粋)・セキュリティ・ログの5つは必須**。この5つは、該当しないと思っても一旦立ち止まって深く検討し、対策として実装できることは極力実装する方針で臨む(考えた末に本当に不要と判断した場合のみ、その理由を一言書く。安易に「特になし」で済ませない)。残りの見出しはこの機能が実際に関わる場合だけ書き、関わらないものは見出しごと省略する(「該当なし」とは書かない)。

1. **処理フロー**(必須) — `##`見出し。個々の処理はこの下に`###`見出しで並べる
   - **処理の呼び名**(`###`見出し) — 業務的な言葉にする(✗「calcPapaChildcare67の変更」 → ○「通常育休(前期67%)の開始日を決める処理」)。関数名・実装対象ファイルなどの実装詳細はtasks.mdに書く
   - **対象** — この処理が何に対して行われるか
   - **手順** — 日本語の文章で書く番号付きステップ(変数名・数式は使わない)。分岐がある場合は「〜の場合は…、そうでない場合は…」と書く。単純な1つの計算(例:「出産予定日の42日前」)のようにビジネスルールの文章だけで手順が自明なものは書かない。その処理固有のエラー時の振る舞い(例:「保存に失敗した場合は、エラーを画面に伝えず処理を終える」)はここに書く。複数の処理にまたがる方針がある場合のみ、下記のエラーハンドリング見出しにまとめる
   - **シーケンス図**(ブラウザ・Supabase・認証基盤など複数アクター間のやり取りがある処理のみ) — 該当する処理の配下にMermaidコードブロック(`sequenceDiagram`)を埋め込む。手順の文章が正であり、図は俯瞰用の補助(後述「Mermaid図の埋め込みルール」参照)
   - **関連するビジネスルール** — `requirements.md#見出し`

2. **バリデーション**(入力値に対する検証ロジックが必要な場合のみ) — 検証する項目・条件と、NGの場合の扱いを簡潔に書く。単純な必須入力チェックなど自明なものは省略してよい。

3. **エラーハンドリング**(必須) — 通信エラー・想定外の例外など、複数の処理にまたがる共通のエラー処理方針を積極的に検討して書く。個々の処理固有のエラー時の振る舞いは処理フローの手順に直接書けば足りるため、ここでは機能全体を通じた方針に絞る。

4. **関連するファイル(抜粋)**(必須) — フォルダ構成のルール自体はCLAUDE.mdにあるため、ここでは「新規に追加するファイル」「既存でこの機能から使う共通処理(Supabaseクライアント・共通コンポーネントなど)」だけを列挙する。
   ```
   app/ikukyu/lib/saveResult.ts (新規)
   app/lib/supabaseClient.ts (既存の共通クライアントを利用)
   ```

5. **データベース設計**(Supabaseのテーブルに保存・参照する場合のみ) — テーブル名と、この機能で追加・使用するカラムのみを書く。RLSやテーブル運用方針などアプリ横断の決定は`docs/adr/`を参照し重複させない。
   ```
   ### ikukyu_results
   | カラム | 型 | 補足 |
   |---|---|---|
   | leave_start_date | date, nullable | パパのみ入力。未入力ならNULL |
   ```

6. **API設計**(サーバー側の処理を新設する場合のみ) — このプロジェクトは静的配信+ブラウザからSupabase直書きの構成(`docs/adr/0001-user-input-database.md`)でAPI Route Handlerを基本的に持たないため、通常は不要。将来的にサーバー処理を追加する機能でのみ書く。

7. **画面設計**(新しい画面・表示項目・操作を追加する場合のみ) — 表示項目と操作を箇条書きで。レイアウトの詳細・型定義は実装に委ねる(非自明なUI仕様はrequirements.mdのUI/UX要件に書く)。新しい画面を追加する場合は、[/requirementの要件ヒアリング](../requirement/SKILL.md#要件ヒアリング)で複数案を提示し確定した画面イメージを踏まえて書く(design段階で新たに画面追加が判明した場合も同じルールに従い、案を複数提示してから選んでもらう)。前述の「UIデザインの確定(Step0)」を行った機能では、採用したデザイン候補の概要とv0生成コードへの参照もここに書く。

8. **コンポーネント設計**(再利用可能な新しいコンポーネントを追加する場合のみ) — Propsの型と役割だけを簡潔な表にする。

9. **状態管理**(複数の処理・画面にまたがって共有する状態がある場合のみ) — 何を・どこで保持するか(useState/Context/URLパラメータなど)を一言で書く。状態が3つ以上、または遷移に条件分岐があるときは、状態遷移図(Mermaid `stateDiagram-v2`)をこの見出しに埋め込む(文章が正、図は補助)。

10. **セキュリティ**(必須) — 入力値のサニタイズ、個人情報・機微情報の扱い方など、この機能固有のリスクを積極的に洗い出し、対策できることは設計に盛り込む。RLSやanonキーの権限方針などアプリ横断の決定は`docs/adr/`を参照し重複させない。

11. **パフォーマンス**(この機能で特別な考慮が必要な場合のみ) — 例: 大量データのページネーション、重い計算のメモ化・非同期化など。

12. **ログ**(必須) — この機能で出力すべきログ(処理の開始・終了・失敗など)を積極的に検討して書く。出力するログはタイミング・内容・ログレベルを簡潔に書く。

# Mermaid図の埋め込みルール

design.mdに図を入れる場合(シーケンス図・状態遷移図)は以下に従う:

- 図はMermaidコードブロックとして該当見出しに直接埋め込む(専用ファイル・画像は作らない)
- **図は日本語の文章を置き換えない。** 処理フロー等の文章が正であり、図は俯瞰用の補助。`[n]`採番・spec-coverageの対象は従来どおり文章側
- 作成条件に該当する場合のみ作る(無条件に全処理へ図を付けない)
- ノード名・ラベルは業務的な言葉/1行1エッジ/図の直後に正となる文章へのリンク、などの書き方ルールは[architecture-workflow](../architecture-workflow/SKILL.md)の「Mermaidの書き方ルール」に従う

# tasks.mdの書き方

設計をもとに実装可能な最小単位に分解する。対象の関数名・ファイル名などの実装詳細はここに書いてよい。タスクを細かく分けるほどAIの生成精度が上がりレビューもしやすくなる。

タスクの並び順・粒度は、各タスクを🔴Red(失敗するテストを書く)→🟢Green(最小実装)→🔵Refactorの順で完結できる単位にする(TDDサイクルの進め方・詳細は[/implementation](../implementation/SKILL.md)を参照)。冒頭に`> TDDで進める。各タスクは 🔴 Red(失敗するテストを書く) → 🟢 Green(最小実装) → 🔵 Refactor の順で進める。`という一文を入れる。

- 前述の「UIデザインの確定(Step0)」を行った機能では、最初のタスク「v0生成コードの取り込み・整形」だけはTDDサイクルの対象外になる([/implementation](../implementation/SKILL.md#ui統合タスクv0生成コードの取り込み)参照)。このタスクには🔴🟢🔵のラベルを付けず、代わりに「(TDD対象外)」と明記する
- 変更頻度が低く設計が単純な機能は requirements.md のみで可(例: legal)

# architecture.mdへの反映

新規specフォルダの作成・廃止や、spec間の依存関係の変化がある場合、`specs/<アプリ名>/architecture.md`が存在すれば機能マップも合わせて更新する(存在しなければこの手順は不要。作成基準・書き方は[architecture-workflow](../architecture-workflow/SKILL.md)を参照)。あわせて、architecture.md内の図への影響も確認する: システム構成図(使うコンポーネント・外部サービスの増減)、コンポーネント図(spec横断の依存の変化)、ER図(使用テーブルの追加・リレーションの発生)に変化があれば同じ変更で図も更新する(図だけが古くなることの禁止。[architecture-workflow](../architecture-workflow/SKILL.md)の「更新ルール」参照)。

# 完了時の次ステップ案内

design.md/tasks.mdが書けたら、[/requirement](../requirement/SKILL.md)が作った早期仕様PRの同じブランチに追加コミット・push する(新しいPRは作らない。手順は[/pr](../pr/SKILL.md)の「早期仕様PR」参照)。3点セット(requirements.md/design.md/tasks.md)が揃ったら、[/spec-review](../spec-review/SKILL.md)(仕様レビュー)へ進むことを案内する。この時点ではまだコード(テストを含む)を書かない。

この時点の成果物(design.md/tasks.md)はコミット・pushして早期仕様PRに乗っているため、ここでcompactや新しいセッションへの切り替えを行っても支障はない。切り替える場合は、新しいセッションの名称(前のセッションと同じ<機能名>に次工程名を()で添えた形。例: `<機能名>(仕様レビュー)`)と、次のセッションにそのまま貼り付けられるプロンプトをコードブロックで提示してから終える(例: `/spec-review を実行してください。対象は specs/<アプリ名>/<機能名>/、ブランチ feature/<機能名>(PR #<番号>)です。`)。
