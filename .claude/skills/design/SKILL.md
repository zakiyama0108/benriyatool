# design.mdの書き方

requirements.mdのビジネスルールを「どんな手順・分岐で処理するか」を日本語の文章(変数名・数式なし)で書く**処理フロー**を中心に、この機能が実際に関わるファイル・DB・画面などを確認用に書き足す。フォルダ構成の一般ルールや、プロジェクト全体の非機能要件・設計方針はCLAUDE.md/requirements.mdの領分のためここには書かない。分岐・複数ステップのロジックが1つもない機能(例: 純粋なルーティング変更)は、design.md自体を作らずrequirements.mdのみで完結してよい。

以下の見出しのうち**処理フロー・エラーハンドリング・関連するファイル(抜粋)・セキュリティ・ログの5つは必須**。この5つは、該当しないと思っても一旦立ち止まって深く検討し、対策として実装できることは極力実装する方針で臨む(考えた末に本当に不要と判断した場合のみ、その理由を一言書く。安易に「特になし」で済ませない)。残りの見出しはこの機能が実際に関わる場合だけ書き、関わらないものは見出しごと省略する(「該当なし」とは書かない)。

1. **処理フロー**(必須) — `##`見出し。個々の処理はこの下に`###`見出しで並べる
   - **処理の呼び名**(`###`見出し) — 業務的な言葉にする(✗「calcPapaChildcare67の変更」 → ○「通常育休(前期67%)の開始日を決める処理」)。関数名・実装対象ファイルなどの実装詳細はtasks.mdに書く
   - **対象** — この処理が何に対して行われるか
   - **手順** — 日本語の文章で書く番号付きステップ(変数名・数式は使わない)。分岐がある場合は「〜の場合は…、そうでない場合は…」と書く。単純な1つの計算(例:「出産予定日の42日前」)のようにビジネスルールの文章だけで手順が自明なものは書かない。その処理固有のエラー時の振る舞い(例:「保存に失敗した場合は、エラーを画面に伝えず処理を終える」)はここに書く。複数の処理にまたがる方針がある場合のみ、下記のエラーハンドリング見出しにまとめる
   - **関連するビジネスルール** — `requirements.md#見出し`

2. **バリデーション**(入力値に対する検証ロジックが必要な場合のみ) — 検証する項目・条件と、NGの場合の扱いを簡潔に書く。単純な必須入力チェックなど自明なものは省略してよい。

3. **エラーハンドリング**(必須) — 通信エラー・想定外の例外など、複数の処理にまたがる共通のエラー処理方針を積極的に検討して書く。個々の処理固有のエラー時の振る舞いは処理フローの手順に直接書けば足りるため、ここでは機能全体を通じた方針に絞る。

4. **関連するファイル(抜粋)**(必須) — フォルダ構成のルール自体はCLAUDE.mdにあるため、ここでは「新規に追加するファイル」「既存でこの機能から使う共通処理(Supabaseクライアント・共通コンポーネントなど)」だけを列挙する。
   ```
   app/ikukyu/lib/saveResult.ts (新規)
   app/lib/supabaseClient.ts (既存の共通クライアントを利用)
   ```

5. **データベース設計**(Supabaseのテーブルに保存・参照する場合のみ) — テーブル名と、この機能で追加・使用するカラムのみを書く。RLSやテーブル運用方針などアプリ横断の決定は`docs/adr/`を参照し重複させない。
   ```
   ### ikukyu_results
   | カラム | 型 | 補足 |
   |---|---|---|
   | leave_start_date | date, nullable | パパのみ入力。未入力ならNULL |
   ```

6. **API設計**(サーバー側の処理を新設する場合のみ) — このプロジェクトは静的配信+ブラウザからSupabase直書きの構成(`docs/adr/0001-user-input-database.md`)でAPI Route Handlerを基本的に持たないため、通常は不要。将来的にサーバー処理を追加する機能でのみ書く。

7. **画面設計**(新しい画面・表示項目・操作を追加する場合のみ) — 表示項目と操作を箇条書きで。レイアウトの詳細・型定義は実装に委ねる(非自明なUI仕様はrequirements.mdのUI/UX要件に書く)。

8. **コンポーネント設計**(再利用可能な新しいコンポーネントを追加する場合のみ) — Propsの型と役割だけを簡潔な表にする。

9. **状態管理**(複数の処理・画面にまたがって共有する状態がある場合のみ) — 何を・どこで保持するか(useState/Context/URLパラメータなど)を一言で書く。

10. **セキュリティ**(必須) — 入力値のサニタイズ、個人情報・機微情報の扱い方など、この機能固有のリスクを積極的に洗い出し、対策できることは設計に盛り込む。RLSやanonキーの権限方針などアプリ横断の決定は`docs/adr/`を参照し重複させない。

11. **パフォーマンス**(この機能で特別な考慮が必要な場合のみ) — 例: 大量データのページネーション、重い計算のメモ化・非同期化など。

12. **ログ**(必須) — この機能で出力すべきログ(処理の開始・終了・失敗など)を積極的に検討して書く。出力するログはタイミング・内容・ログレベルを簡潔に書く。

# tasks.mdの書き方

設計をもとに実装可能な最小単位に分解する。対象の関数名・ファイル名などの実装詳細はここに書いてよい。タスクを細かく分けるほどAIの生成精度が上がりレビューもしやすくなる。

タスクの並び順・粒度は、各タスクを🔴Red(失敗するテストを書く)→🟢Green(最小実装)→🔵Refactorの順で完結できる単位にする(TDDサイクルの進め方・詳細は[/implementation](../implementation/SKILL.md)を参照)。冒頭に`> TDDで進める。各タスクは 🔴 Red(失敗するテストを書く) → 🟢 Green(最小実装) → 🔵 Refactor の順で進める。`という一文を入れる。

- 変更頻度が低く設計が単純な機能は requirements.md のみで可(例: legal)

# architecture.mdへの反映

新規specフォルダの作成・廃止や、spec間の依存関係の変化がある場合、`specs/<アプリ名>/architecture.md`が存在すれば機能マップも合わせて更新する(存在しなければこの手順は不要。作成基準・書き方は[architecture-workflow](../architecture-workflow/SKILL.md)を参照)。

# 完了時の次ステップ案内

3点セット(requirements.md/design.md/tasks.md)が揃ったら、[/spec-review](../spec-review/SKILL.md)(仕様レビュー)へ進むことを案内する。この時点ではまだコード(テストを含む)を書かない。
