# 仕様作成の3ステップ

`specs/<アプリ名>/<機能名>/` に requirements.md → design.md → tasks.md の順で作成する。

- **Step1 requirements.md(要件定義)**
  「何を作るか(WHAT)」「なぜその仕様にしたか(根拠)」を言語化する。数式・変数名は使わず日本語の言葉で書く(正確な計算式はコードとテストに委ねる)。技術的な実装方法(HOW)はここでは書かない。
  以下の見出しをテンプレートとして使う(該当しないものは省略してよい)。

  1. **概要** — 機能名・目的・優先度
  2. **ユーザーストーリー** — 「〜としては、〜したい」という利用者視点の要求
  3. **機能要件** — 実装する機能と入出力を言葉で説明する
  4. **ビジネスルール・制約** — 数値・条件などのルールと、その根拠(法令・公式資料・過去の意思決定など)を必ずセットで書く。特殊な入力やエラー時にどう振る舞うべきかも、条件付きのルールとしてこの見出しの中に書く(例:「賃金日額が上限を超える場合、上限額を基準に計算する」)。項目が複数ある場合は`###`見出しで分ける(テストとの対応付けがしやすくなる)

  機能要件・ビジネスルール・制約など、個別にテストを対応させたい箇条書きには見出し内で連番の`[n]`を振る(見出しが変わればまた`[1]`から振り直してよい、グローバルな採番ではない)。

  ```markdown
  ### 出産手当金
  - [1] 対象: ママのみ
  - [2] 対象期間: 出産予定日の42日前(産前)から出産日の56日後(産後)までの98日間
  - [3] 給付額: 対象期間中、賃金日額の3分の2を支給する
  ```

  概要・ユーザーストーリー・スコープ外など、そもそもテスト対象にならない見出しには`[n]`を振らなくてよい(見出し単位でスキップ登録の対象になる)。
  5. (任意)**非機能要件・依存関係・制約条件・UI/UX要件** — 関係する場合のみ書く。無理に埋めない

- **Step2 design.md(設計)**
  requirements.mdのビジネスルールを「どんな手順・分岐で処理するか」を日本語の文章(変数名・数式なし)で書く**処理フロー**を中心に、この機能が実際に関わるファイル・DB・画面などを確認用に書き足す。フォルダ構成の一般ルールや、プロジェクト全体の非機能要件・設計方針はCLAUDE.md/requirements.mdの領分のためここには書かない。分岐・複数ステップのロジックが1つもない機能(例: 純粋なルーティング変更)は、design.md自体を作らずrequirements.mdのみで完結してよい。

  以下の見出しのうち**処理フローのみ必須**。それ以外はこの機能が実際に関わる場合だけ書き、関わらないものは見出しごと省略する(「該当なし」とは書かない)。

  1. **処理フロー**(必須) — `##`見出し。個々の処理はこの下に`###`見出しで並べる
     - **処理の呼び名**(`###`見出し) — 業務的な言葉にする(✗「calcPapaChildcare67の変更」 → ○「通常育休(前期67%)の開始日を決める処理」)。関数名・実装対象ファイルなどの実装詳細はtasks.mdに書く
     - **対象** — この処理が何に対して行われるか
     - **手順** — 日本語の文章で書く番号付きステップ(変数名・数式は使わない)。分岐がある場合は「〜の場合は…、そうでない場合は…」と書く。単純な1つの計算(例:「出産予定日の42日前」)のようにビジネスルールの文章だけで手順が自明なものは書かない。その処理固有のエラー時の振る舞い(例:「保存に失敗した場合は、エラーを画面に伝えず処理を終える」)はここに書く。複数の処理にまたがる方針がある場合のみ、下記のエラーハンドリング見出しにまとめる
     - **関連するビジネスルール** — `requirements.md#見出し`

  2. **バリデーション**(入力値に対する検証ロジックが必要な場合のみ) — 検証する項目・条件と、NGの場合の扱いを簡潔に書く。単純な必須入力チェックなど自明なものは省略してよい。

  3. **エラーハンドリング**(複数の処理にまたがる共通のエラー処理方針がある場合のみ) — 例: 通信エラー時の共通リトライ方針、エラーの握りつぶし方針など。個々の処理固有のエラー時の振る舞いは処理フローの手順に直接書けば足りることが多い。

  4. **関連するファイル(抜粋)**(既存の共通基盤(Supabaseクライアント・共通コンポーネントなど)に触れる場合のみ) — フォルダ構成のルール自体はCLAUDE.mdにあるため、ここでは「新規に追加するファイル」「既存でこの機能から使う共通処理」だけを列挙する。
     ```
     app/ikukyu/lib/saveResult.ts (新規)
     app/lib/supabaseClient.ts (既存の共通クライアントを利用)
     ```

  5. **データベース設計**(Supabaseのテーブルに保存・参照する場合のみ) — テーブル名と、この機能で追加・使用するカラムのみを書く。RLSやテーブル運用方針などアプリ横断の決定は`docs/adr/`を参照し重複させない。
     ```
     ### ikukyu_results
     | カラム | 型 | 補足 |
     |---|---|---|
     | leave_start_date | date, nullable | パパのみ入力。未入力ならNULL |
     ```

  6. **API設計**(サーバー側の処理を新設する場合のみ) — このプロジェクトは静的配信+ブラウザからSupabase直書きの構成(`docs/adr/0001-user-input-database.md`)でAPI Route Handlerを基本的に持たないため、通常は不要。将来的にサーバー処理を追加する機能でのみ書く。

  7. **画面設計**(新しい画面・表示項目・操作を追加する場合のみ) — 表示項目と操作を箇条書きで。レイアウトの詳細・型定義は実装に委ねる(非自明なUI仕様はrequirements.mdのUI/UX要件に書く)。

  8. **コンポーネント設計**(再利用可能な新しいコンポーネントを追加する場合のみ) — Propsの型と役割だけを簡潔な表にする。

  9. **状態管理**(複数の処理・画面にまたがって共有する状態がある場合のみ) — 何を・どこで保持するか(useState/Context/URLパラメータなど)を一言で書く。

  10. **セキュリティ**(この機能固有のセキュリティ上の考慮が必要な場合のみ) — 例: 入力値のサニタイズ、個人情報・機微情報の扱い方など。RLSやanonキーの権限方針などアプリ横断の決定は`docs/adr/`を参照し重複させない。

  11. **パフォーマンス**(この機能で特別な考慮が必要な場合のみ) — 例: 大量データのページネーション、重い計算のメモ化・非同期化など。

  12. **ログ**(この機能で独自にログを出力する場合のみ) — 出力するタイミング・内容・ログレベルを簡潔に書く。

- **Step3 tasks.md(タスク分解)**
  設計をもとに実装可能な最小単位に分解する。対象の関数名・ファイル名などの実装詳細はここに書いてよい。タスクを細かく分けるほどAIの生成精度が上がりレビューもしやすくなる。

  - 変更頻度が低く設計が単純な機能は requirements.md のみで可(例: legal)

# 仕様承認ゲート

3点セットを作成したら一旦PRを出し、ユーザーの確認・承認を得るまでコード(テストを含む)は書き始めない。この段階ではrequirements.mdの先頭(タイトル直下)に `> ステータス: 仕様確認中(未実装)` という行を入れる。

この行がある間、そのフォルダのrequirements.md/design.mdは`check:spec-coverage`のチェック対象・CI失敗条件から除外される(🚧仕様確認中として表示される)。これは「テスト不要」という恒久的な判断ではなく、「まだ実装していないだけ」という一時的な状態を表すものなので、`scripts/spec-coverage-skip.json`には登録しない。実装(🔴Redのテスト)に着手し、仕様項目に対応するテストが書けたらこの行を削除する(削除を忘れても、対応するテストが増えた項目から順に✅表示に切り替わるだけで実害はない)。

実装フェーズに入ってからのTDDサイクル・テストの書き方・PR作成手順は [tdd-testing](../tdd-testing/SKILL.md) を参照する。

# テストとの対応付け

- テストの`// 仕様: specs/.../requirements.md#見出し-n`コメントは、基本的にrequirements.mdの`[n]`を振った箇条書きを参照する(`[n]`がない見出しは見出し名だけを書く)。design.mdの処理フローは、requirements.mdで既にテストされているロジックを実装向けに書き下したものなので、原則テストからは参照しない。
- ビジネスルールの箇条書きは「〜の場合、〜になること」という文体に揃えておくと、そのままテストの`it()`に転記しやすい。
- `npm run check:spec-coverage`で、requirements.md/design.mdの各項目に対応するテストが書けているかをチェックできる(CIでも実行され、❌が残っていると失敗する)。見出し名や`[n]`は完全一致で照合するため、表記ゆれがあると❌になる点に注意する。
- design.mdの処理フロー項目や、そもそもテスト不要な見出し(概要・ユーザーストーリー・スコープ外など)は、`scripts/spec-coverage-skip.json`に理由を添えて登録する。「❌が出ても気にしなくてよい」という暗黙の例外は設けず、テスト不要と判断した理由を必ずスキップリストに残す。
