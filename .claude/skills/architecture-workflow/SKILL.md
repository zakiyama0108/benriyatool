# architecture.mdとは何か

`specs/<アプリ名>/architecture.md` は、そのアプリ配下の複数specにまたがる全体像を1箇所に集約するドキュメント。以下と役割分担する(重複させない)。

| ドキュメント | 担当範囲 |
|---|---|
| CLAUDE.md | プロジェクト全体で共通のフォルダ規約・コーディング規約 |
| `docs/adr/` | 複数アプリにまたがる技術選定とその理由(DB・ホスティング・認証基盤など) |
| `docs/architecture/` | プロジェクト共通のクラウド・インフラ系の図(インフラ構成図・デプロイメント図など。後述) |
| `specs/<アプリ名>/<機能名>/requirements.md`・`design.md` | 1つの機能(spec)固有の要件・処理フロー・DB項目・セキュリティ |
| `specs/<アプリ名>/architecture.md` | このアプリ配下の複数specをまたぐ全体像(機能マップ・依存関係・このアプリが使うADR/外部サービスの一覧) |

architecture.mdは**参照のハブ**であり、他ドキュメントの内容を転記する場所ではない。技術選定の理由はADRへ、機能ごとの詳細はrequirements.md/design.mdへリンクするだけに留める。「architecture.mdだけ読めばそのアプリの全体を把握できる」ことを目標とする。このためアプリ単位のREADMEは新設しない(アプリ概要・構成図・機能マップ・関連設計書リンクはarchitecture.mdが担う。READMEを別途作ると二重管理になり「図だけが古くなる」事故の温床になる)。セットアップ方法・開発コマンドはルートREADME/CLAUDE.mdの担当であり、アプリ側に転記しない。

# いつ作る/更新するか

- 新しいアプリに着手するタイミングで、[/requirement](../requirement/SKILL.md)の「新規アプリ立ち上げ時のspec分割」と合わせて最初から作成する(具体的なspecが1つしかない段階でも作ってよい。後から待つ必要はない)
- 既存アプリでarchitecture.mdがまだない場合、2つ目以降のspecに着手するタイミングで作成する
- 新規specフォルダの作成・廃止、既存specの依存関係の変化があったときは、[/fix](../fix/SKILL.md)の「仕様(3点セット)への影響を洗い出す」の一環として、機能マップを更新する
- アプリ固有の採用技術・外部サービス・ディレクトリ構成が変わったときも同様に更新する

# 図の運用方針(AI駆動開発向け)

設計図は「人が理解するため」だけでなく「AIが理解・保守しやすいこと」を最優先する。

- 論理構造の図はMermaidコードブロックとして`specs/`配下の既存Markdownに直接埋め込む(専用ファイル・画像は作らない)。Git差分・レビュー・AIによる更新と親和させるため
- **図は日本語の文章を置き換えない。** 処理フロー等の文章が正であり、図は俯瞰用の補助。`[n]`採番・spec-coverageの対象は従来どおり文章側
- **各図種は必須相当**(design.mdの必須見出しと同じ運用)。下表の作成条件に該当する箇所が一つでもあれば、原則その図を描く。該当する箇所が一つもない、と一旦立ち止まって検討した上で判断した場合のみ、その理由を一言添えて省略してよい(安易に省略しない)。一方で、条件に該当しない箇所へ無理に図を足す必要はない(全処理・全画面への一律付与は求めない)

## 論理構造の図の一覧(Mermaid・specs/配下に埋め込み)

これらは要件定義〜設計〜アーキテクチャを通じて、時間がない人でも全体像を図で追えるようにするための図。作成条件を満たす箇所があれば必須相当で描く。

| 図 | 記載先 | 作成条件(満たす箇所があれば必須相当) |
|---|---|---|
| ユースケース図 | requirements.md「ユースケース図」([/requirement](../requirement/SKILL.md)参照) | 利用者(アクター)とできること(ユースケース)がある機能。単一アクター×自明な1ユースケースのみなら省略可 |
| コンテキスト図 | architecture.md「4. コンテキスト図」 | 全アプリ(テンプレどおり必須)。本アプリ・利用者・外部サービスの境界を1枚で |
| システム構成図 | architecture.md「5. システム構成図」 | 全アプリ(テンプレどおり必須) |
| コンポーネント図 | architecture.md「9. コンポーネント図」(機能一覧表の直後) | 複数specにまたがるコンポーネント・lib間依存があるとき |
| ER図 | architecture.md「11. 外部サービス」内(アプリ横断)。spec単位のカラム表(design.md)は現行どおり | アプリの使用テーブルが2つ以上、またはリレーションが生まれたとき |
| シーケンス図 | design.md「処理フロー」配下([/design](../design/SKILL.md)参照) | ブラウザ・Supabase・認証基盤など複数アクター間のやり取りがある処理があるとき |
| 画面遷移図 | design.md「画面設計」配下([/design](../design/SKILL.md)参照) | 画面が複数、または画面内で表示が大きく切り替わる(入力→確認→完了など)とき |
| 状態遷移図 | design.md「状態管理」([/design](../design/SKILL.md)参照) | 状態が3つ以上、または遷移に条件分岐があるとき |

## Mermaidの書き方ルール

- ノード名・ラベルは業務的な言葉にする([/design](../design/SKILL.md)の処理の呼び名の規則と同じ。関数名を図に書かない)
- 差分レビューしやすく書く: 1行1エッジ、ノード定義とエッジ定義を分ける、意味のないリネームをしない
- 図の直後に、その図が表す内容の正となる文章・specへのリンクを置く

# 見出しテンプレート

`specs/<アプリ名>/architecture.md` は以下の見出しで構成する。サマリ・機能一覧表・コンテキスト図・システム構成図は必須(それ以外で該当しない見出しは省略してよい。無理に埋めない)。

0. **サマリ(必須)** — 時間がない人がこの章だけでアプリの全体像をつかめる短い要約。`##`見出しでファイル先頭に置く。アプリが何をするか1行・主要技術・機能一覧表の規模(specがいくつ・何ができるアプリか)・下の「コンテキスト図」「システム構成図」へのリンクを短くまとめる。下の「概要」(1〜2行のメタ情報)とは役割が違う(サマリは中身のTL;DR)
1. **概要** — アプリが何をするアプリか、URLパス、1〜2行で
2. **アーキテクチャの目的** — このアプリ固有の目的のみ(プロジェクト全体の一般論はCLAUDE.mdの担当)
3. **設計方針** — このアプリだからこそ追加で効いてくる方針のみ(CLAUDE.mdの共通方針は書かない)
4. **コンテキスト図(必須)** — Mermaidコードブロックで書く。本アプリを中心に、利用者(アクター)・依存する外部サービス・他アプリとの境界を1枚で俯瞰する(システムの内部構造は描かず、外との関係に絞る)。下の「システム構成図」が内部構成、この図が外部境界、という役割分担
5. **システム構成図** — Mermaidコードブロックで書く(既存のASCIIアートは触るタイミングでMermaidに置換する)。このアプリから見た構成のみを描き、プロジェクト共通インフラの詳細は`docs/architecture/`へリンクする(汎用テンプレートをそのまま貼らない)
6. **アーキテクチャ概要** — 上の図を文章で説明(この文章が正、図は補助)
7. **採用技術** — このアプリが実際に使っている技術のみ。選定理由はADRへのリンクで済ませ再掲しない
   ```markdown
   | 技術 | 用途 |
   |---|---|
   ```
8. **機能一覧表(機能マップ)(必須)** — このアプリ配下のspecフォルダ一覧と、利用者から見た機能名・役割・依存関係。「このアプリで何ができるか」を一覧できる中核の必須見出しで、全specを漏れなく載せる(新規specの追加・廃止時は必ずここを更新する)。architecture.mdをまだ持たない単一specアプリの段階では、requirements.mdのサマリ章の機能要点がこれを兼ねる
   ```markdown
   | spec | 機能(利用者から見て) | 役割 | 依存 |
   |---|---|---|---|
   | simulator | 給付金額をシミュレーションする | 給付金額を計算する | - |
   | save-result | 計算結果を保存する | 計算結果をDBに保存する | simulatorの結果を受け取る |
   ```
9. **コンポーネント図**(複数specにまたがるコンポーネント・lib間依存があるときのみ) — Mermaidで、spec横断で共有されるコンポーネント・libの依存関係を描く。機能一覧表の「依存」列が文章としての正であり、図はその俯瞰
10. **ディレクトリ構成** — `app/<アプリ名>/`配下がCLAUDE.mdの一般規約(components/lib)から逸脱・追加している部分のみ。逸脱がなければ「CLAUDE.mdの規約通り」の一言で済ませる
11. **外部サービス** — このアプリが実際に依存する外部サービス(使用テーブル名など)。選定理由は書かず関連ADRへリンクする。使用テーブルが2つ以上、またはリレーションが生まれたら、この見出しにアプリ横断のER図(Mermaid `erDiagram`)を置く(spec単位のカラム表はdesign.mdの現行どおりで、そちらが正)
    ```markdown
    | サービス | 用途 |
    |---|---|
    ```
12. **関連ADR** — このアプリが依存する`docs/adr/`のリンクのみ列挙(内容は転記しない)
    ```markdown
    - [0001-user-input-database.md](../../docs/adr/0001-user-input-database.md) — 結果保存のDB選定
    ```
13. **セキュリティ** — このアプリ固有のリスクのみ(RLS等の横断的な仕組み自体はADR参照)
14. **技術的制約** — このアプリ固有の制約のみ(プロジェクト全体の制約はADR/CLAUDE.mdの担当)
15. **用語集** — このアプリのドメイン特有の用語のみ(汎用IT用語は書かない)

## 会話ドリブン原則(推測で埋めない)

architecture.mdに書く方針(アーキテクチャの目的・設計方針・採用技術・外部サービス・機能一覧表の役割/依存など)も、[/consult](../consult/SKILL.md)・[/requirement](../requirement/SKILL.md)・[/design](../design/SKILL.md)の会話の中で確認したもの・こちらから提案して合意したものだけを書く。会話に出ていない技術選定・構成方針を推測で埋めない(新規アプリ立ち上げ時に一気に作る場合も、主要な採用技術・外部サービスは提案の形で認識合わせしてから記載する)。

# クラウド・インフラ系の図(docs/architecture/)

クラウドサービスを1つでも使っている場合、以下をプロジェクト共通ドキュメントとして`docs/architecture/`に作成する(アプリ単位ではなくプロジェクト単位。ルートREADMEからリンクする)。

| 図 | 内容 | 記載先 | 作成条件 |
|---|---|---|---|
| インフラ構成図 | 使用している全クラウドサービスと役割・データの流れ・課金/無料枠の境界 | `docs/architecture/infrastructure.md` | クラウドサービスを使っていれば必須 |
| デプロイメント図 | mainマージから本番反映までの経路(CI・ビルド・配信先) | `docs/architecture/deployment.md` | デプロイパイプラインがあれば必須 |
| ネットワーク構成図 | VPC・サブネット・通信経路・境界 | `docs/architecture/network.md` | ネットワーク境界を自分で設計している場合のみ(VPC、プライベート接続、独自DNS/CDN経路の制御など)。フルマネージドサービスの利用だけなら不要(インフラ構成図が兼ねる) |

## 形式の選択

- 構成が単純なうち(サービス数が少なく、配置・アイコンに意味がない)はMermaidで上記.mdに埋め込む
- AWS/GCP等の採用でアイコン・レイアウト・境界の表現に意味が出てきたらDraw.ioへ昇格する:
  - `docs/architecture/<名前>.drawio` を正本とし、README掲載用SVG・資料用PNGを同名で出力する
  - drawio CLIのセットアップと出力手順をADRとして残す
  - README・architecture.mdにはSVGを掲載する(PNGは資料・プレゼン用)
- 昇格の要否は[/retrospective](../retrospective/SKILL.md)の図のスポットチェックで見直す

# 更新ルール(図だけが古くなることの禁止)

設計変更時は、要件定義・設計書・Mermaid図・(あれば)Draw.io図・READMEを**同じPRで同期する**。同期の確認ポイントは各工程Skillに組み込まれている:

- [/design](../design/SKILL.md)「architecture.mdへの反映」: 機能一覧表(機能マップ)に加え、コンテキスト図・システム構成図・コンポーネント図・ER図への影響も確認する
- [/fix](../fix/SKILL.md)「仕様(3点セット)への影響を洗い出す」: 図の同期チェックを含む
- [/spec-review](../spec-review/SKILL.md)チェックリスト: 図が本文・コードと矛盾していないかを確認する
- [/retrospective](../retrospective/SKILL.md): 直近のPRで触ったアプリの図と実態の乖離をスポットチェックする(`docs/architecture/`含む)
- インフラ・デプロイ構成を変えるPR(ホスティング変更・CI変更・外部サービス追加)では、`docs/architecture/`の該当図を同じPRで更新する

ルートREADME.mdのアプリ一覧表(architecture.mdへのリンク)は現行維持し、`docs/architecture/`のインフラ構成図・デプロイメント図へのリンクを追加する。

# 書く際の注意

- 各見出しは「このアプリに関連するものだけ」を書く。プロジェクト全体・複数アプリ共通の内容を見つけたら、architecture.mdに書かずCLAUDE.mdまたは`docs/adr/`側の更新を検討する
- 機能マップの「依存」列と、依存元specのrequirements.mdの依存関係見出しが矛盾しないか確認する(architecture.mdは索引であり、依存の詳細はspec側の`[n]`参照が正)
- architecture.mdはrequirements.mdのような`[n]`採番・仕様承認ゲートの対象外。`npm run check:spec-coverage`のチェック対象にもならない
