> ワークフロー上の位置: 定期作業(開発ループ外)。ずれが見つかったら [/fix](../fix/SKILL.md) または軽微ならそのまま修正PRへ

# 実行タイミング

四半期に1回を目安。specフォルダが増えた・大きなリファクタをした直後にも実行するとよい。

# チェックリスト

## spec-coverage
- [ ] `npm run check:spec-coverage`を実行し、❌が放置されていないか
- [ ] `scripts/spec-coverage-skip.json`の各エントリについて、理由が現行ルールを指しているか(存在しないファイル・廃止したドキュメントへの参照が残っていないか)、スキップ対象の見出しがまだ実在するか

## 仕様書と実装の乖離
- [ ] 各`requirements.md`の「スコープ外」に、実はもう実装済みの項目が残っていないか
- [ ] ビジネスルールの記述と実装コード(`app/<アプリ名>/lib/`の定数・分岐)が一致しているか
- [ ] `> ステータス: 仕様確認中(未実装)`の行が、実装済みのspecに残っていないか(逆に、未実装specから消えていないか)

## architecture.md
- [ ] 機能マップのspec一覧が`specs/<アプリ名>/`配下のフォルダ実態と一致しているか
- [ ] 依存関係の記述が各specのrequirements.mdの依存関係と矛盾していないか
- [ ] 採用技術・外部サービスの表が現在の構成(package.json・wrangler.toml・ADR)と合っているか

## その他
- [ ] `[n]`採番に欠番・重複がないか(途中削除で歯抜けになった箇所は詰めずに現状維持でよいが、テストコメントとの対応が生きているか確認する)
- [ ] `docs/adr/`のステータス(提案中のまま運用が定着しているものは「採用」へ更新)

# ずれの直し方

- 仕様の内容そのものに関わるずれ(ビジネスルールと実装の不一致など) → [/fix](../fix/SKILL.md)のフローへ(承認要否も/fixの基準で判断)
- ドキュメント整理だけで済む軽微なずれ(skip.jsonの理由文言、architecture.mdの表、ステータス行の削除漏れなど) → 棚卸し結果をまとめて1本の修正PR([/pr](../pr/SKILL.md))にしてよい
- どちらか迷うものはユーザーに一覧で提示して判断を仰ぐ

# 完了時の次ステップ案内

棚卸し結果(問題なし/修正した項目/持ち越した項目)を一覧でユーザーに報告する。修正PRを出した場合はマージ後に[/release-check](../release-check/SKILL.md)へ(ドキュメントのみの変更でもデプロイは走るため、Step1の確認だけで足りる)。
