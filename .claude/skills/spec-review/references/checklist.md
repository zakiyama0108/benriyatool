# 仕様レビューのチェックリスト

spec-reviewerエージェント(またはエージェントを使えない状況で直接レビューするメインスレッド)が読むファイル。レビュー実施者以外はこのファイルを読まない(トークン節約のため[SKILL.md](../SKILL.md)本体から分離している)。

# レビューの注意事項

- **レビュー中は対象を修正しない。** 指摘の報告に徹する(修正は[/resolve](../../resolve/SKILL.md)の仕事)
- **好みの問題は指摘しない。** 指摘には必ずルール上の根拠([/requirement](../../requirement/SKILL.md)・[/design](../../design/SKILL.md)のテンプレート、CLAUDE.mdの規約、既存specとの整合性など)を添える。根拠を示せない指摘は出さない
- **良い点も必ず1つ以上挙げる**
- **レビュー結果に応じて次のステップを案内する**(テンプレート末尾の案内を必ず含める)

# チェックリスト

## requirements.md
- [ ] ユーザーストーリーが利用者視点(「〜としては、〜したい」)で書かれているか
- [ ] ビジネスルールの数値・条件に根拠(法令・公式資料・過去の意思決定)が添えられているか
- [ ] テストを対応させたい箇条書きに`[n]`が振られているか。「〜の場合、〜になること」の文体になっているか
- [ ] 数式・変数名・実装方法(HOW)が混ざっていないか
- [ ] スコープ外(今回やらないこと)が明記されているか
- [ ] タイトル直下に`> ステータス: 仕様確認中(未実装)`の行があるか(新規specの場合)
- [ ] 他specへの依存が内容の書き写しでなく`<spec名>/requirements.md#見出し-n`の参照形式になっているか
- [ ] ユーザー入力の極端なパターン(未入力・境界値・想定外の値)に対する挙動がビジネスルールとして決まっているか

## design.md(作成している場合)

形式:
- [ ] 必須5見出し(処理フロー・エラーハンドリング・関連するファイル・セキュリティ・ログ)が検討されているか。安易な「特になし」で済ませていないか
- [ ] 処理の呼び名が業務的な言葉になっているか(関数名・ファイル名などの実装詳細が混ざっていないか)
- [ ] 手順が日本語の文章で書かれ、分岐が「〜の場合は…、そうでない場合は…」の形で網羅されているか

中身:
- [ ] requirements.mdの全ビジネスルールが処理フローのいずれかでカバーされているか(設計漏れがないか)
- [ ] 境界値・特殊ケース(期間の境目、上限額ちょうど、未入力・NULL、月末日など)が分岐として現れているか
- [ ] エラーハンドリングが起こりうる失敗ごとに具体的か(何が失敗したら・ユーザーに何を見せ・処理を継続するか中断するかまで決まっているか)
- [ ] セキュリティがこの機能固有のリスクを検討しているか(保存する個人情報が必要最小限か、ブラウザから直接書き込める構成の影響を考えたか)。詳細な観点は後述の「セキュリティ設計レビュー」に従う
- [ ] データベース設計がある場合、型・nullableに根拠があるか。既存カラムと重複していないか
- [ ] 画面設計がある場合、正常表示以外の状態(ローディング・エラー・空・未入力)が考慮され、既存画面と用語・操作感が一貫しているか
- [ ] 省略された任意見出し(バリデーション・パフォーマンスなど)が本当に該当しないか。逆に、書かれている見出しで実装に委ねてよい詳細まで書き込んでいないか
- [ ] 設計がプロジェクト構成(静的配信+ブラウザからSupabase直書き、`docs/adr/`の決定)と矛盾なく実現可能か

図(Mermaid・埋め込んでいる場合):
- [ ] 図が本文(処理フローの手順・状態管理の文章)・requirements.mdと矛盾していないか(文章が正、図は俯瞰用の補助)
- [ ] 作成条件([architecture-workflow](../../architecture-workflow/SKILL.md)の「論理構造の図の一覧」)に該当するのに図がないか。逆に、条件に該当しない処理へ無理に図を付けていないか
- [ ] ノード名・ラベルが業務的な言葉になっているか(関数名・ファイル名が図に混ざっていないか)
- [ ] 図の直後に、その図の正となる文章・specへのリンクが置かれているか

## tasks.md(作成している場合)
- [ ] 各タスクが🔴Red→🟢Green→🔵Refactorで完結できる粒度か
- [ ] 冒頭にTDD宣言文があるか
- [ ] design.mdの全処理がいずれかのタスクでカバーされているか
- [ ] タスクの並び順が依存関係の順(先に必要なものが先)になっているか

## セキュリティ設計レビュー(design.mdを作成している場合)

設計書に以下の観点でセキュリティ対策が盛り込まれているかを確認する。**目的は「設計段階でセキュリティ要件・設計が十分に考慮されているか」の確認であり、実装コードのレビューではない**(実装レベルのチェックは/implementation-reviewの仕事)。この機能に該当しない観点は飛ばしてよいが、「該当なし」の根拠が設計・プロジェクト構成(静的配信+ブラウザからSupabase直書き、`docs/adr/`の決定)から説明できるかを確認する。

認証(Authentication):
- [ ] 認証が必要な機能と不要な機能が明確に設計されているか
- [ ] 認証方式(OAuth、OIDC、JWT、セッションなど)が適切か
- [ ] 未認証アクセスの扱いが定義されているか

認可(Authorization):
- [ ] ユーザー権限ごとのアクセス制御が設計されているか
- [ ] 他ユーザーのデータへアクセスできない設計になっているか
- [ ] 管理者権限が必要な操作が明確になっているか

入力値検証(Input Validation):
- [ ] 外部入力に対するバリデーション方針が定義されているか
- [ ] SQL Injection・NoSQL Injection・XSS・Command Injection・Path Traversalなどを防ぐ設計になっているか

データ保護:
- [ ] 個人情報・機密情報の取り扱いが定義されているか
- [ ] 保存時・通信時の暗号化が必要なデータが整理されているか
- [ ] APIレスポンスやログに不要な機密情報を含めない設計になっているか

通信・暗号化:
- [ ] HTTPS/TLSを前提とした設計になっているか
- [ ] 必要に応じて保存データの暗号化が考慮されているか

シークレット管理:
- [ ] APIキーやDB接続情報などの認証情報をSecret Managerや環境変数で管理する前提になっているか
- [ ] ハードコーディングを前提とした設計になっていないか

レート制限・DoS対策:
- [ ] 公開APIや認証APIなど、レート制限が必要な箇所が整理されているか
- [ ] 想定される負荷や悪用への対策が設計されているか

ログ・監査:
- [ ] 必要な監査ログ・操作ログが設計されているか
- [ ] ログへ機密情報を出力しない方針になっているか

エラーハンドリング:
- [ ] 利用者へ内部情報を漏らさないエラー設計になっているか
- [ ] システム内部情報やスタックトレースを返さない設計になっているか

## 3点セットの整合性
- [ ] requirements↔design↔tasksの間で矛盾(designにだけある処理、requirementsにだけあるルール)がないか
- [ ] 新規spec作成 vs 既存spec更新の判断([/requirement](../../requirement/SKILL.md)のStep0)が正しいか
- [ ] `specs/<アプリ名>/architecture.md`がある場合、機能マップ(spec一覧・依存関係)と矛盾しないか。architecture.md内の図(システム構成図・コンポーネント図・ER図)に影響する変更(外部サービス・使用テーブル・spec間依存の増減)があるのに図が更新されていない、という状態になっていないか

# 指摘の重要度

| 重要度 | 意味 | 扱い |
|---|---|---|
| 🔴 must | 承認できない問題(要件の欠落・矛盾、根拠のないビジネスルール、テンプレート必須項目の欠落) | 修正するまで/prに進まない |
| 🟡 should | 修正が望ましい問題(表現の曖昧さ、`[n]`の振り忘れ、文体の不統一) | 原則今回対応する |
| 🟢 info | 参考情報・質問・提案 | 対応は任意 |

## セキュリティ指摘の重要度

セキュリティ設計上の懸念は Critical / High / Medium / Low の4段階で評価し、テンプレートの「セキュリティ設計レビュー」節に「問題点・想定されるリスク・推奨する設計改善案」をセットで報告する。/prに進めるかの判定は既存の重要度に対応付ける:

| セキュリティ重要度 | 意味 | 対応する既存重要度 |
|---|---|---|
| Critical | 悪用が容易で影響が重大(認証・認可の欠落、機密情報の露出など) | 🔴 must |
| High | 重大なリスクだが悪用に条件がある、または影響範囲が限定的 | 🔴 must |
| Medium | リスクはあるが緩和策が存在する、設計の明文化漏れ | 🟡 should |
| Low | 望ましい改善・多層防御の提案 | 🟢 info |

# フィードバックのテンプレート

```markdown
## 仕様レビュー結果: <承認(指摘なし) / 要修正(🔴n件・🟡n件・🟢n件)>

### 対象
specs/<アプリ名>/<機能名>/

### 良い点
- (必ず1つ以上)

### 指摘事項
| # | 重要度 | 対象 | 指摘内容 | 根拠 |
|---|---|---|---|---|
| 1 | 🔴 must | requirements.md#ビジネスルール | ... | ... |

### セキュリティ設計レビュー
<懸念がなければ「懸念なし」と一言書く。指摘件数はタイトル行の🔴/🟡/🟢の件数にも含める>
| # | 重要度 | 対象 | 問題点 | 想定されるリスク | 推奨する設計改善案 |
|---|---|---|---|---|---|
| S1 | High(🔴相当) | design.md#セキュリティ | ... | ... | ... |

### 次のステップ
- 🔴/🟡あり → /resolve で修正し、再レビューを受ける
- 指摘なし(🟢のみ) → /pr で仕様承認PRを作成する
```
