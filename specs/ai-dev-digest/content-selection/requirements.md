# 要件定義: 情報源ウォッチリストと採用基準

## 概要
- 機能名: 情報源ウォッチリストと採用基準
- 目的: 「相当ランクの高い、信頼できる発信者」の情報だけを扱いつつ、日によって記事内容が空になることのないよう、日次で取り上げるトピックを定量的に選び出す
- 優先度: 高

## ユーザーストーリー
- 運営者として、無名の発信者や偶然バズっただけのコンテンツではなく、業界で実績のある組織・発信者の情報だけを扱ってほしい
- 運営者として、その日は基準を満たすトピックが少なくても、記事が空にならず一定量のコンテンツが毎日出てほしい
- 運営者として、基準を満たすトピックが慢性的に少ない状態が続く場合は、基準そのものが厳しすぎる可能性に気づけるようにしてほしい

## 機能要件

### 情報源(ウォッチリスト)
- [1] 対象とする情報源は次の18件に限定する(固定リスト運用とし、記載以外の発信者・組織をエージェントが自律的に追加することはしない)

| 名称 | 区分 | チャンネル |

| OpenAI | 公式組織 | 公式ブログ・YouTube |
| LangChain | 公式組織 | 公式ブログ・YouTube |
| AWS | 公式組織 | AI/ML関連の公式ブログ・YouTube |

| Google Developers | 公式組織 | 公式ブログ(blog.google の開発者向けカテゴリ) |
| VS Code | 公式組織 | 公式ブログ(code.visualstudio.com。エディタのAI機能リリースノート等) |

| Fireship | 個人YouTube | YouTube |

- [2] X(Twitter)は対象に含めない(根拠: 公式APIが有料(Basic tier月額$100〜)で、無料枠では発信者のフォロワー数取得や検索が実質できないため)。X中心の発信者(LangChain CEOのHarrison Chase等)は、LangChain公式の発信でカバーする

### 採用基準(種別ごとの定量判定)
- [4] 公式組織の新着投稿(ブログ記事・YouTube動画)は、原則としてすべて採用候補にする(根拠: 発信量が少なく、内容の信頼性が高いため)
- [5] 個人YouTubeチャンネルは、直近`youtubeCandidateVideoCount`本(初期値5)の動画それぞれについて、そのチャンネルの直近動画群の平均再生回数を明確に上回るかを判定し、上回る動画を採用候補にする(根拠: 登録者数や再生数の絶対値による閾値では、チャンネルごとの規模差を吸収できないため。相対的にそのチャンネル内で特に話題になった動画を拾う。評価対象を最新1本に限ると、投稿直後で再生数が伸びていない動画しか判定できず、数日前に投稿されて伸びた動画を取りこぼすため、直近数本をまとめて評価する。2026-08運営者相談に基づき評価対象を最新1本から直近5本に拡大)
- [6] 個人ブログ(種別`individual-blog`。Simon Willison・Interconnects・Martin Fowler)は、新着投稿を原則として採用候補にする。ただし公式RSSが返す本文が`minIndividualBlogBodyChars`文字(初期値150)未満の投稿は、要約に足る情報がない(ポッドキャスト回の告知など)ため採用候補にしない
- [7] Qiitaは、直近`qiitaMaxAgeDays`日(初期値60。約2ヶ月)以内に公開された記事のうち、いいね数30以上のものを採用候補にする(根拠: 公開直後の記事はいいねが付く前で採用条件を満たしにくいため、少し時間が経った記事も対象にできるようにする。2026-08運営者相談に基づき「新着」の定義を「直近2ヶ月以内」に変更。対象期間を広げたことで同じ記事が複数日にわたり条件を満たしうるが、[14]の掲載済み除外で日をまたいだ再掲は防ぐ)
- [8] Zennの新着記事は、公式RSSフィードで新着を発見し、要約のために開く記事の公開ページに表示されているいいね数を読み取って、30以上のものを採用候補にする(根拠: Zennには公式のいいね数取得APIがなく、非公式APIの利用は避ける方針のため。要約のためにどのみち開く公開ページの表示値を使うことで、非公式APIを使わずに済む)

### 1日の掲載件数
- [9] 1日のダイジェストに含めるトピック数は3〜5件とする
- [10] 上記[4]〜[8]の基準を満たす採用候補が3件に満たない日でも、実在する候補(基準未達の候補を含む)が1件以上あれば、その件数のまま掲載する(3件に届かせるために架空の話題を作ることはしない)。基準未達の候補で採用したトピックには、基準を満たしていない旨を分かりやすく示す(具体的な表示方法は設計で詰める)。収集した候補が実在するものも含め1件もない日のみ、その日はスキップする
- [11] [10]による基準未達での掲載が発生した場合、その事実(発生日・情報源・基準からの乖離度合いなど)を記録する。記録した内容は[watchlist-review/requirements.md](../watchlist-review/requirements.md)の月次見直しで参照し、基準未達が慢性的に続く場合は採用基準そのものを見直す(根拠: 基準未達が続くのは基準設定が実態に合っていないサインであるため)

### 話題の関連性(種別を問わない横断フィルター)
- [12] 情報源・種別ごとの採用基準(上記[4]〜[8])を満たしていても、内容が「AI駆動開発」(ソフトウェア開発エンジニア向けの生成AI活用・開発ツール・モデル動向等)との関連性が薄い場合は、採用候補から除外する。医療・ヘルスケアなど、AI技術の応用事例ではあるが開発エンジニア向けの実務性に乏しい分野の話題が典型例(2026-08運営者フィードバックに基づき追加。根拠: 公式組織の新着投稿は上記[4]により無条件で採用候補になり、話題の内容面の関連性はこれまで判定されていなかったため、開発者向けとは言えない話題(AIによる小児希少疾患の診断支援。OpenAI公式YouTubeより、2026-08-05公開)が掲載された)
  - 判定方法は原文タイトルに対する決定的なキーワード判定とする(2026-08第2次改定で確定。詳細はdesign.md「話題の関連性フィルタを適用する処理」参照)

### 情報源内の重複掲載の抑制(種別を問わない横断フィルター)
- [13] 個人ブログ(上記[6]、種別`individual-blog`)は、同日に複数の採用候補が挙がった場合でも、1日の掲載枠にはその情報源から1件までとする(2026-08運営者フィードバックに基づき追加。根拠: 個人ブログは公式組織の告知と異なり、著者が同日に複数の短い投稿をすることがあり、実際に2026-08-15にSimon Willisonのsqlite-utilsの関連リリースに関する候補2件、2026-08-24に同氏のAIモデルの価格・選び方に関する候補2件が同日に採用され、「毎日同じような話が重複している」「特定の話題に集中しすぎている」との指摘を運営者から受けた。公式組織([4])は発信量が少なく告知の性質上重複が起きにくいため対象としない)
  - 複数候補がある場合は、公開日時が最も新しいもの1件を残し、他は候補から除外する(判定方法の詳細はdesign.md「情報源内の重複を抑制する処理」参照)
  - 対象とする種別は`criteria.json`の`duplicateSuppressionSourceTypes`で管理し、今後の月次見直しで対象種別を追加・削除できるようにする

### 掲載済み記事の再掲抑制(種別を問わない横断フィルター)
- [14] 過去に公開したダイジェスト記事で既に取り上げた記事・動画(元URLが一致するもの)は、採用条件を満たしていても当日の採用候補から除外する(全種別が対象。2026-08運営者相談・フィードバックに基づき追加。根拠: [7]でQiitaの対象期間を「直近2ヶ月以内」に、[5]で個人YouTubeを直近5本評価に広げたことで、同じ記事・動画が複数日にわたり採用条件を満たし続け、日をまたいで再掲されうるようになったため。従来は各情報源が「最新N件」しか返さないことに暗黙に依存して再掲を防いでいた)
  - 判定は`content/ai-dev-digest/articles/*.json`に記録済みの全トピックの元URL(`sourceUrl`)との完全一致で行う(判定方法の詳細はdesign.md「掲載済み記事を除外する処理」参照)

## ビジネスルール・制約

### データ取得方法
- [1] 各情報源の取得は、公式API・公式RSSフィード・公式の埋め込み機能・公開ページの閲覧の範囲にとどめ、非公式API・認証回避・利用規約の想定を超えた高頻度アクセスは行わない(根拠: 各サービスの利用規約遵守。Zennのいいね数取得([9]参照)はこの原則の具体例)

### 情報源の健全性監視
- [2] 日次実行のログに、情報源ごとに「収集した候補件数(取得失敗はその旨)」を出力する。候補件数が0件だった情報源は警告として明示する(根拠: フィードURLの変更・廃止などで特定の情報源が無言で機能を停止することがあり、実際にLangChain公式ブログ・DeepLearning.AIのThe Batchが数週間気づかれず候補ゼロだった。日次のログに毎回残すことで、[watchlist-review/requirements.md](../watchlist-review/requirements.md)の月次見直しが「慢性的に0件の情報源」を拾い、URL修正・入れ替えの判断材料にできる)

## 依存関係
- 選定されたトピックは[article-detail/requirements.md](../article-detail/requirements.md)で表示される
- 選定候補の翻訳・要約は[content-generation/requirements.md](../content-generation/requirements.md)のルールに従って行われる
- ウォッチリスト・採用基準の変更は[watchlist-review/requirements.md](../watchlist-review/requirements.md)の月次見直しでのみ行う(このspec自身の基準値を日次運用の中で自動的に変更することはしない)
- 収集・選定の実行タイミングは[daily-publish/requirements.md](../daily-publish/requirements.md)に従う

## スコープ外
- プラットフォームを横断した統合スコアによるランキング化(単位の異なる指標を正規化して比較することはしない)
- ウォッチリストへの新規情報源の自動発掘(固定リスト運用)。YouTube全体・Web全体のキーワード検索で話題を拾う案も検討したが、(1)「無名の発信者や偶然バズっただけのコンテンツは扱わない」というこのspecの根幹方針と衝突する、(2)YouTube Data APIの検索は1回100クオータ・Web検索APIは実質有料で「基本無料」の運用方針に合わない、の2点から採らない(2026-08運営者相談)。個人YouTubeチャンネル内での話題動画の拾い上げは[5]の直近5本評価で対応する
- ポッドキャストの取得・要約
- X(Twitter)の取得
