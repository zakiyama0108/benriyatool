# 設計: 翻訳・要約・記事執筆のルール

## 設計の前提(エージェントの推論とコードの役割分担)

[content-selection/design.md](../content-selection/design.md)の方針と対になる整理として、本specでは次のように役割を分ける(要件はロジックの実装形態まで指定していないため設計判断):

- **エージェントの推論に委ねる**: 選定された候補(content-selectionの出力)から、日本語の紹介文としての翻訳・要約を書く行為そのもの。意味理解・言い換えが本質的にLLMの得意領域であり、コード化になじまない
- **決定的なコードに任せる**: 要約の文字数チェック、記事タイトルの生成、YouTube動画IDの抽出、著作権配慮のガードレール文言の提示。これらは「揺れてはいけない/機械的に導出できる」性質のため、エージェントの推論結果ではなく固定のコード・固定文言にする

エージェント(GitHub Actionsのワークフローから`scripts/ai-dev-digest/generate-content.ts`経由でヘッドレス起動するClaude Code CLI。2026-08改定: 当初はClaude Routinesの自律的な推論を想定していたが、[daily-publish/design.md](../daily-publish/design.md)「実行環境の前提」の改定によりGitHub Actions+API呼び出しに変更。2026-08第2次改定: Anthropic Messages APIの従量課金呼び出しから、運営者個人のClaude Code Pro/Maxサブスクリプション認証によるClaude Code CLIヘッドレス実行に変更した。理由は運用コスト(APIの従量課金)を避け、既契約のサブスクリプション利用枠内で完結させるため。トレードオフとして、この利用枠(5時間ごと・週次の上限)は運営者本人のClaude Code対話利用と共有される。生成に失敗した場合の扱いはdaily-publish/design.md「エラーハンドリング」参照)が翻訳・要約を書く際に従うべきルールは、[requirements.md](requirements.md)と本design.mdそのものを直接参照させる(別ファイルにプロンプト文を複製しない。日次実行の運用手順は[daily-publish/design.md](../daily-publish/design.md)で「このrequirements.md/design.mdの内容をプロンプトに含めて実行する」という指示として組み込む)。元記事・元動画の内容把握には、Claude Code CLIに標準搭載されたWebFetch/WebSearchツールを使い、スクリプト側では原文を事前取得しない(別途ツール定義を宣言する必要はない)。

## 処理フロー

### 要約を書く処理(エージェントの推論)
- 対象: content-selectionが選定した1件の候補(原文タイトル・元URL・情報源種別)
- 手順:
  1. 元記事・元動画の内容を把握し、固定4観点(`benefit`🚀メリット/`whatsNew`💡新規性/`how`🛠仕組み/`howToUse`🎯活用法、この順序で固定。requirements.md#要約-5・#要約-12)それぞれについて書く。観点の数・順序をトピックに応じて変えることはしない(2026-08修正: 従来は2〜4セクション程度をトピックに応じて自由に章立てしていたが、見出しだけで価値が伝わる固定構成に変更した)
  2. 各観点について、常時表示される導入文(60〜120字程度)と、展開表示される詳細文を書く。4観点の詳細文の合計が1000〜1500字程度になるようにする(requirements.md#要約-2〜4)
  3. 各観点の見出しは、テーマ名(例:「LangChainのDeep Agents」)ではなく結論・メリット・変化を含む一文(例:「AIにブラウザ操作まで任せられるようになる」)にする。見出しだけで観点の価値が伝わることを確認する(requirements.md#要約-9)
  4. 導入文は詳細文の冒頭を抜き出したものではなく、その観点の要点をまとめた独立した一文とする。詳細文はその要点を掘り下げた解説にする(requirements.md#要約-3)
  5. 各観点の導入文・詳細文は、専門用語や仕組みの説明から書き始めず、結論・メリット(WHAT)→なぜ重要か(WHY)→どう実現しているか(HOW)の順で説明する(requirements.md#要約-10)
  6. 記事に含める情報は、開発効率・生産性・コスト等への直接的な影響を最優先とする優先順位(requirements.md#要約-11)に従って選び、優先度の高い情報ほど上位の観点・早い文で扱う
  7. 原文の逐語訳ではなく、内容を踏まえた解説として書く(requirements.md#翻訳-1)。原文の段落構成・表現の順序をなぞらず、独自の構成に再構成する。原文の詳細な展開・結論・具体的な数値を網羅的に転記しない(requirements.md#要約-6)
  8. `🎯活用法`観点では、記事の内容を実際のAI駆動開発にどう応用できるかを示す(例: 今すぐ試す価値がある/今後使う可能性が高い/考え方として参考になる/現時点では直接使う必要はない/まだ成熟していない。requirements.md#要約-12)。固定4観点いずれも、記事に書かれていない内容を推測で断定しない。ただし`🎯活用法`の「自分への影響」は記事内容から合理的に判断することを許容し、推測を含む場合はその旨が伝わる書き方にする(requirements.md#エージェントの逸脱防止-10)
  9. トピック全体の重要度を5段階(★1〜★5)で判定する。基準は「自分のAI駆動開発にどれだけ影響するか」であり、記事・情報源の知名度では判断しない(requirements.md#重要度-13〜14)
  10. 見出し(タイトル)は原文タイトルの逐語的な言い換えにとどめず、各観点の見出しと同じ考え方(requirements.md#要約-9)で、この記事から何が得られるか(結論・要点)が見出しだけで伝わるように作成する(2026-09改定。従来は「原文タイトルを日本語で簡潔に言い換えたもの」とのみ定めていた)
  11. 出典情報(発信者名・見出し・元URL)を必ずセットにする(requirements.md#記事の構成-7)
  12. **応答は必ず指定のJSONオブジェクト単体とし、運営者に判断を仰ぐ質問文や選択肢の提示を返さない**(ヘッドレス実行のため質問しても応答する相手がおらず、返答が非JSONになると後述のとおり当該トピックの生成失敗として扱われる)。WebFetch/WebSearchで元URLの内容を十分に取得できなかった場合でも、確認できた情報(タイトル・発信者・情報源種別など)の範囲で書けるところまで書いてJSONを返す。それも困難な場合は無理に内容を創作せず、後段で失敗と判定できるよう`summary`を`null`にしたJSONを返す(いずれの場合も聞き返さない)
- 応答JSONの形式(2026-08改定。固定4観点+重要度):
  ```json
  {
    "heading": "この記事から何が得られるか(結論・要点)が伝わる見出し",
    "importance": 4,
    "summary": {
      "benefit": { "heading": "結論・メリットを含む見出し", "teaser": "60〜120字程度の導入文", "detail": "展開表示する詳細文" },
      "whatsNew": { "heading": "...", "teaser": "...", "detail": "..." },
      "how": { "heading": "...", "teaser": "...", "detail": "..." },
      "howToUse": { "heading": "...", "teaser": "...", "detail": "..." }
    }
  }
  ```
  取得困難な場合は`"summary": null`を返す(旧仕様の空`sections`配列に相当する失敗シグナル。下記「要約の分量を検証する処理」・app/ai-dev-digest/lib/generateContent.tsの`isUsableContent`が判定する)
- 適用するガードレール文言(daily-publishの実行指示に必ず含める。requirements.md#エージェントの逸脱防止-8の具体化):
  > この記事で扱ってよい話題は、content-selectionの採用基準に基づき選定された候補のみである。選定候補に含まれない話題(政治・時事ネタ等)を、AI駆動開発に関連付けて新たに追加してはならない。要約(導入文・詳細文とも)は独自の章立てで再構成した解説とし、原文の段落構成・表現の順序をそのままなぞってはならない。原文の詳細な数値・結論を網羅的に転記してはならない。
- 関連するビジネスルール: requirements.md#翻訳-1、requirements.md#要約-2〜6・9〜12、requirements.md#重要度-13〜14、requirements.md#記事の構成-7、requirements.md#著作権への配慮-1〜6・9、requirements.md#エージェントの逸脱防止-8・10

### 要約の分量を検証する処理(決定的なコード)
- 対象: エージェントが書いた`summary`(固定4観点`benefit`/`whatsNew`/`how`/`howToUse`の組)・`importance`
- 手順:
  1. `summary`が`null`、またはオブジェクトでない場合は不正とする(旧仕様の「配列長2件未満」チェックに相当する失敗シグナル)。`benefit`/`whatsNew`/`how`/`howToUse`の4キーがすべて揃っており、各観点の`heading`/`teaser`/`detail`が空文字でないことを確認する(2026-08修正: 従来は可変長`sections`配列の長さチェックだったが、固定4観点オブジェクトの4キー存在チェックに変更した)
  2. 各観点の`teaser`(導入文)の文字数が40字未満、または140字を超える場合は不正とする。「60〜120字程度」の「程度」を、最初に導入した要約分量チェック(目安100〜150字に対し±20字の許容幅)と同じ絶対値の許容幅として解釈し、40〜140字とする(要件は許容幅を定めていないため設計判断。値そのものは変更なし)
  3. 4観点の`detail`(詳細文)を連結した文字数が800字未満、または1700字を超える場合は不正とする。「1000〜1500字程度」の「程度」を、既存の要約分量チェック(目安100〜150字に対し80〜170字の許容幅=約±20%)と同じ比率の許容幅として解釈し、800〜1700字とする(値そのものは変更なし)
  4. `importance`が1〜5の整数でない場合は不正とする(requirements.md#重要度-13)
  5. 不正な場合は[article-detail](../article-detail/design.md)のスキーマ検証(`parseArticle`)がエラーとして扱い、ビルドを失敗させる(article-detail/design.md#エラーハンドリング)。2026-08以前に生成された既存記事データ(可変長`sections`配列)は本検証の対象外とし、従来通りの検証(配列長2件以上・detail合計800〜1700字)を維持する(article-detail/design.md#バリデーション参照。無理な再生成・変換は行わない)
- 関連するビジネスルール: requirements.md#要約-2〜5、requirements.md#重要度-13〜14

### 記事タイトルを導出する処理(決定的なコード)
- 対象: 記事の日付
- 手順:
  1. `YYYY年M月D日のAIニュース`のような固定テンプレートに日付を当てはめてタイトルを生成する(要件は「その日全体の記事タイトルを生成する」とのみ定め、方法は設計に委ねられているため。エージェントに毎回自由生成させると、誇張表現や話題の先取り(逸脱)のリスクがあるため、日付から一意に決まる決定的な処理にする)
  2. エージェントはタイトルの生成に関与しない(記事JSONにもタイトルを含めない。article-detail/design.md「前提: 記事データの形式」参照)
- 関連するビジネスルール: requirements.md#記事の構成-8

### YouTube動画IDを抽出する処理(決定的なコード)
- 対象: 情報源のURL(YouTube動画の場合)
- 手順:
  1. URLの形式(`youtube.com/watch?v=`、`youtu.be/`等)から動画IDを抽出する
  2. 抽出できた場合のみ、記事データの`Topic.youtubeVideoId`に設定する(article-detail側は`youtube-nocookie.com`ドメインで公式埋め込みプレーヤーを表示する。requirements.md#著作権への配慮-6)
  3. 抽出できない形式のURLの場合は`youtubeVideoId`を設定せず、通常の出典リンク表示のみにする(要件[6]の「可能であれば」に対応)
- 関連するビジネスルール: requirements.md#著作権への配慮-6

## エラーハンドリング

- 導入文・詳細文の分量超過・過少は記事データのビルド時バリデーション(article-detail/design.md)でCI失敗として検知する。翻訳・要約の内容そのもの(意味的な正確さ・話題の妥当性・原文をなぞっていないか)は自動検証できないため、エージェント自身の執筆時点でのガードレール遵守に委ね、事後の自動チェックは設けない(限界として明記する)
- YouTube動画ID抽出処理は、失敗しても記事生成自体を止めない(処理フロー参照。埋め込み表示ができないだけで出典リンクは引き続き機能する)
- エージェントの応答から指定のJSONオブジェクトを抽出できない場合(上記手順8で防げなかった聞き返し・説明文のみの応答・空の`sections`など)は、その候補1件の生成失敗として扱う。1件の生成失敗をその日全体の失敗に波及させない具体的な扱い(リトライ回数・除外して継続する制御・利用枠枯渇との区別)は、この生成処理を1候補ずつ起動するオーケストレーション側([daily-publish/design.md](../daily-publish/design.md)「エラーハンドリング」「1日分の記事を生成する処理」)で定める

## セキュリティ

- 生成される要約・見出しは訪問者に表示される文章のため、通常のReactレンダリングでエスケープされる(article-detail/design.md#セキュリティと同様、追加のサニタイズは不要)
- 著作権リスクへの対応は、分量の上下限(コードで強制)・独自の章立て構成(ガードレール文言で指示)・出典明記(スキーマで必須化)・利用規約への条項追記の4点で構成する(requirements.md#著作権への配慮-1〜6・9)。ただし翻訳・要約の「質」(本当に独自の解説として再構成されているか、原文をなぞっていないか)はコードで保証できない限界がある点を明記しておく(上記エラーハンドリング参照)。2026-08、可変長セクションから固定4観点への変更後も、主要な緩和策(独自の再構成・数値結論の網羅転記回避・出典明記)は変わらず適用されるためリスク評価の結論は変わらない(requirements.md#著作権への配慮-9)

## ログ

- 導入文・詳細文の分量検証結果(合否・実際の文字数)は、article-detailのビルド時バリデーションのエラーメッセージとしてCIログに出力される(article-detail/design.md#ログ)
- 翻訳・要約の生成過程自体(エージェントの推論内容)は本アプリのログ設計の対象外とする(GitHub Actionsのワークフロー実行ログとして別途残る運用上の記録であり、アプリコードが管理する対象ではないため)

## 利用規約への反映

requirements.md#利用規約への反映-7の条項をそのまま`specs/legal/requirements.md`(知的財産の項目)と`app/legal/page.tsx`(「4. 知的財産」セクション)に追記する。文面はrequirements.mdに明記済みの以下をそのまま使う(新たな文言を作らない):

> 本サービスの一部機能(AI駆動開発ダイジェスト)では、第三者が公開した動画・記事等を独自の視点で解説する目的で、出典元へのリンクとともに要約(全文の翻訳・転載ではない)を掲載している。著作権者から掲載内容の修正・削除の要望があれば、問い合わせ先まで連絡があり次第、速やかに対応する。
