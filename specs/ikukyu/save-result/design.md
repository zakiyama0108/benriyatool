# 設計: 計算結果の保存

## 処理フロー

### 合計取得日数を算出する処理
- 対象: 入力内容(モード・出産予定日・(パパのみ)育休開始日・育休終了予定日)
- 手順:
  1. ママの場合は産前休業開始日(出産予定日の42日前)を、パパの場合は育休開始日(未入力なら出産予定日)を休み始めの日とする
  2. 休み始めの日から育休終了予定日までの日数を数える
- 関連するビジネスルール: requirements.md#機能要件-2

### テストデータかどうかを判定する処理
- 対象: 保存を実行する時点の実行環境と表示中ページのURL
- 手順:
  1. 開発サーバー(`npm run dev`)で動いているビルドならテストデータと判定する(Next.jsがビルド時に埋め込む実行モードで判別する)
  2. そうでなければ、表示中ページのURLのクエリに`test=1`が付いているかを見て、付いていればテストデータと判定する
  3. どちらにも該当しなければテストデータではないと判定する
- 関連するビジネスルール: requirements.md#テストデータの判定-1〜3

### 計算結果を保存する処理
- 対象: 「計算する」ボタン押下で得られた入力内容と計算結果
- 手順:
  1. 入力内容・計算結果の合計額・合計取得日数・テストデータ判定の結果(`is_test`)を1件のレコードとしてまとめる
  2. Supabaseの`ikukyu_results`テーブルへの保存を試みる
  3. 保存に失敗した場合は、エラーを画面に伝えず処理を終える(計算結果の表示はそのまま続ける)
- 関連するビジネスルール: requirements.md#機能要件-1、requirements.md#機能要件-3、requirements.md#エッジケース・例外処理-1

## エラーハンドリング

- 保存は分析用のベストエフォート処理のため、失敗の種類(通信エラー・RLS拒否・カラム不一致など)を問わずエラーをユーザーに伝えず、計算結果の表示を継続する(個々の振る舞いは処理フロー参照)
- この方針の裏返しとして、テストフラグ導入時にカラム追加前の新コードが動くとINSERTが全件失敗しても画面上は気づけない。対策として、マイグレーション(下記データベース設計)を実装の動作確認より前に単独PRで適用しておき、リリース直後に[data-check](../../../.claude/skills/data-check/SKILL.md)の件数確認を行う

## データベース設計

### ikukyu_results
| カラム | 型 | 補足 |
|---|---|---|
| id | uuid | 共通カラム(`docs/adr/0001`)。DB側で自動採番 |
| created_at | timestamptz | 共通カラム。DB側で自動設定 |
| mode | text | ママ/パパの区分 |
| monthly_salary | integer | 月給 |
| due_date | date | 出産予定日 |
| leave_start_date | date, nullable | パパのみ入力。未入力・ママはNULL |
| leave_end_date | date | 育休終了予定日 |
| total_amount | integer | 給付金の合計額 |
| total_leave_days | integer | お休みの合計取得日数 |
| is_test | boolean, not null, default false | **今回追加。** テスト・動作確認データの判別フラグ(共通カラム化の決定は`docs/adr/0001`) |

### マイグレーション(テストフラグ導入時に1回だけ適用)

スキーマ変更は`docs/adr/0003`の基盤に従い、`supabase/migrations/`のSQLファイルとしてコード管理し、mainマージ時にCIが自動適用する(手動でSQLエディタから実行しない)。

以下の内容のマイグレーションファイルを、**実装より先に単独のPRとしてマージして適用しておく**(カラムがないと新コードのINSERTが失敗し、握りつぶされて気づけないため。実装コードと同じPRに同梱すると、マージ前のローカル動作確認の時点でカラムが存在しない)。

```sql
-- 1. テストフラグカラムの追加(既定はfalse=実データ。旧コードからのINSERTにはis_testが含まれないため、既定値で実データ扱いになる)
alter table ikukyu_results add column is_test boolean not null default false;

-- 2. 既存レコードの一括更新(requirements.md#テストデータの判定-4: 導入前のデータはすべてテストデータ扱い)
update ikukyu_results set is_test = true;
```

適用順序の補足: 適用後〜新コード(実装PR)のデプロイ完了までの間に旧コードから保存されたレコードは`is_test = false`(実データ)になる。導入前データの一括更新は上記2.の1回きりで、二重適用はマイグレーション基盤の適用履歴管理が防ぐ。

## セキュリティ

- `test=1`は誰でも付けられる公開URLパラメータだが、付けた場合に起きるのは「そのレコードが集計から除外される」ことだけで、他人のレコードの閲覧・改ざんはできない(anonキーはINSERTのみ、`docs/adr/0001`)。悪意ある大量投稿はフラグの有無に関わらず従来からのスパム懸念(同ADR)であり、この変更で悪化しない
- 実ユーザーが誤って`test=1`付きURLを開いて実データが失われる経路を作らないよう、サイト内のリンク・共有導線に`test=1`を含めない
- `is_test`カラム自体は個人情報を含まない。月給などの機微な入力値をURLパラメータに載せない方針(architecture.md#セキュリティ)は従来どおりで、`test=1`はこの方針に抵触しない

## ログ

保存失敗時もコンソール等へのログ出力は行わない(既存方針の維持)。静的配信でサーバーを持たず、ブラウザのコンソールログは運営者が収集できないため、出力しても気づく手段にならない。保存の異常(件数の急減など)には[data-check](../../../.claude/skills/data-check/SKILL.md)の定期確認で気づく運用とする。
