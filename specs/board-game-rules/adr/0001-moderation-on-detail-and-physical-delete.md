# 0001. ゲームモデレーションを詳細画面へ集約し、削除を物理削除にする

> board-game-rules アプリ固有のADR。全アプリ横断の技術選定は[docs/adr/](../../../docs/adr/)を参照する。

## ステータス
承認済み(2026-08-20)

## コンテキスト
- board-game-rules の管理画面([admin/requirements.md](../admin/requirements.md))は当初、運営者向けに「登録済みゲームの一覧」を持ち、その一覧からゲーム1件ごとの編集・削除・紹介画像の差し替え・投稿元写真の照合閲覧・コメント削除を行う設計だった。
- 一方、利用者が実際にゲームを閲覧する画面はゲーム詳細([game-detail/requirements.md](../game-detail/requirements.md))であり、運営者が「この登録内容はおかしい」と気づくのも詳細画面を見ているときである。モデレーション対象の実体(分類情報・ルール本文・紹介画像・コメント)はすべて詳細画面に表示されるため、モデレーション用に別途ゲーム一覧を管理画面へ持つと、同じ情報を二重に持ち、対象ゲームへ辿り着く導線も二系統になる。
- ゲームの削除は当初、`deleted_at` を立てる論理削除を採用していた。理由は「削除後も運営者が通報・元写真を照合できるようレコードを残す」「誤削除を復元できる」余地を残すためだった。しかし運用を検討した結果、削除したゲームについて後から通報・元写真を見返す運用も、誤削除の復元も不要と判断した。削除前の元の申請内容は、別テーブルの登録依頼レコード(`board_game_rules_game_requests`)が独立して残るため、緩いバックアップとして機能する。

## 決定
1. **ゲーム1件ごとのモデレーション操作(分類情報・ルール本文の編集、削除、紹介画像の差し替え・削除、投稿元写真の照合閲覧、コメント削除)は、そのゲームの詳細画面(game-detail)に、運営者ログイン時のみ表示する管理者導線として持たせる。** 管理画面(admin)は、複数ゲームを横断して確認する運用(通報一覧・登録依頼一覧)とログイン・アクセス制御を担う。通報一覧から対象ゲームの詳細画面へ遷移してモデレーションを行う。
   - 「元写真の照合閲覧」「コメント削除」も、他のゲーム個別操作と同じく詳細画面に置く(モデレーション対象がその画面に集まっているため、操作の場を一箇所にまとめる)。
2. **ゲームの削除は物理削除とする。** `board_game_rules_games` の該当行を DELETE し、`deleted_at` 列は廃止する(論理削除を使わないため)。
   - 削除時、そのゲームに紐づく子レコード(コメント・お気に入り・通報)は、子テーブルの外部キーを `ON DELETE CASCADE` にすることでゲーム行の DELETE に連動して自動削除する。紹介画像パス(`intro_photo_paths`)は games 行の列のため行削除で一緒に消える。
   - Storage の実ファイル(投稿元写真・紹介画像の実体)は削除しない。投稿元写真の実ファイルは登録依頼レコードと Storage パスを共有しており、削除すると依頼側のバックアップ写真まで巻き添えになるため。参照されなくなった Storage 実ファイル(孤児オブジェクト)の掃除は、将来の定期棚卸し運用(games・game_requests の全パス参照と突き合わせ、どこからも参照されない実ファイルのみ一括削除)で対応する。
3. **アクセス制御は画面側の出し分けに依存せず、DB の RLS と Storage のアクセスポリシーで担保する。** 詳細画面に載る運営者向けの書き込み(games の UPDATE/DELETE、comments の DELETE、Storage の UPDATE/DELETE、投稿元写真の SELECT)は、いずれも運営者本人(`admin_emails`)のみに限定する。これは[ADR-0006](../../../docs/adr/0006-admin-screen-oidc-rls.md)の「読み取り専用」テンプレートに対する[ADR-0007](../../../docs/adr/0007-runtime-llm-server-and-writable-admin.md)の書き込み例外の延長であり、書き込みの場が管理画面から詳細画面に広がっても方針は同じ。

## 影響
- 管理画面からゲーム一覧・編集フォーム・元写真照合・コメント削除の各機能が無くなり、詳細画面に運営者ログイン時の導線として実装され直す。物理削除には、games への運営者向け DELETE ポリシー追加・子テーブル外部キーの `ON DELETE CASCADE` 付け替え・`deleted_at` 列の削除・公開取得 RLS の `deleted_at is null` 条件の除去を伴うマイグレーションが必要になる。
- 削除は不可逆になる(復元機能を持たない)。誤削除への防御は、削除操作前の確認ステップで担保する。
- 孤児 Storage 実ファイルは蓄積しうるが、定期棚卸し運用で回収する前提とし、即時削除は行わない(依頼側バックアップの保全とシンプルさを優先)。

## 検討した代替案
| 候補 | 見送り理由 |
|---|---|
| 管理画面のゲーム一覧を維持したまま編集・削除を続ける | 詳細画面と同じ情報・導線を二重に持ち続けることになる。モデレーション対象は詳細画面に集まっているため、操作の場を分ける利点がない |
| 論理削除を維持する | 削除後の通報・元写真の見返し、誤削除の復元がいずれも不要と判断したため、`deleted_at` を持ち続ける意味がない。使わない列・条件を残すと取得クエリ・RLS が無駄に複雑になる |
| 物理削除時に Storage 実ファイルも即時削除する | 投稿元写真は登録依頼レコードと Storage パスを共有しており、即時削除すると依頼側バックアップを壊す。共有参照を確認してから消すロジックは複雑で、定期棚卸しで一括回収する方が単純かつ安全 |
