# 0006. 認証付き管理画面のOIDC/RLS方針

## ステータス
提案中

## コンテキスト
- 育休シミュレーターの保存データ(`ikukyu_results`)を、運営者本人が自作UI(一覧・検索など)で閲覧する管理画面を追加したい。従来の閲覧・集計は[ADR-0004](0004-agent-readonly-db-access.md)の読み取り専用ロールやSupabaseダッシュボードで行う運用だったが、ダッシュボードでは扱いにくい見せ方・スマホからの閲覧をしたいニーズが出た
- 制約: サイトはNext.jsの静的エクスポートでCloudflare Workersに配信しており、サーバー機能を一切持たない([ADR-0001](0001-user-input-database.md)、[specs/ikukyu/architecture.md](../../specs/ikukyu/architecture.md))。この構成は維持する。したがってクライアントに埋め込めるキーは`anon`(INSERT専用)のみで、`service_role`は絶対に埋め込めない
- 管理画面には2つの層がある。**①ページアクセス制御**(誰が管理画面URLを開けるか)と、**②DB読み取り権限**(そのページが`ikukyu_results`をSELECTできるか)。①をどれだけ固めても②が解けなければ「ログインできるが中身が空の画面」になる。静的サイトのまま②を解くには、認証で得たJWTでRLSを通す以外に素直な方法がない
- [ADR-0001](0001-user-input-database.md)は「ログインが必要なアプリを追加する場合はSupabase Authを使う」と予告済み。今回はそれを具体的なプロバイダ選定とRLSパターンとして確定させる
- 認証は無料の外部SaaSでOIDC、可能ならパスキーを使いたい。管理画面の利用者は運営者本人のみ

## 決定
**Supabase AuthのGoogle OIDCで運営者本人をログインさせ、取得したJWTでRLSを通して`ikukyu_results`を閲覧する。静的エクスポート構成は維持する(Supabase JSはクライアント動作でサーバー不要)。**

- **①②を1つのJWTで解決する**: ブラウザでSupabase AuthのGoogle OIDCログイン → JWT取得 → そのJWTでSupabaseにSELECT。ページアクセスもDB読み取りも同じ認証セッションで賄う
- **RLSに第3のポリシーを追加する**: `ikukyu_results`に対し「認証済み(`authenticated`)かつ運営者のメール(`auth.jwt()->>'email'`が運営者アドレス)のときだけ全行SELECT可」というポリシーを追加する。既存の`anon`のINSERT専用ポリシー・[ADR-0004](0004-agent-readonly-db-access.md)の読み取り専用ロールのSELECTポリシーは現状維持で、これらとは別物
- **パスキーはIdP経由で実現する**: アプリ自身をネイティブなWebAuthn Relying Partyにはしない。運営者のGoogleアカウント側をパスキー(生体認証)で保護しておけば、管理画面のGoogle OIDCログインは体感としてパスキー認証になる。アプリ側の実装はOIDCのみで、WebAuthnの自前実装は持たない
- **アプリ側の認証手段はGoogle OIDCの1本に絞る**: パスワード認証・メールのマジックリンクなど、他の認証手段は用意しない(パスキーより弱い経路からログインされるのを塞ぐため)
- **IdP(Googleアカウント)側の要件を運用前提として課す**: 管理画面にログインするGoogleアカウントには、次の**2つを別個の対策として**課す。これらは1つの認証手順(パスキー＋2段階認証の合わせ技)ではない点に注意する
  1. **パスキーを登録し、ログインはパスキーで行う** — パスキーでのログインは1ステップで完了し、パスワードの入力も2段階認証の確認コードも不要になる(パスキー自体が端末の所持と生体認証・PINの通過を証明するため、Googleは2段階認証の2つ目のステップを省略する)
  2. **2段階認証を有効にする** — これは1.のパスキーログインに手順を足すためではない。パスキーを登録してもGoogleアカウントにはパスワードによるログイン経路が別に残り続けるため、その弱い経路を保護するための対策である。アプリ側の認証手段をOIDCの1本に絞っても、Googleアカウントがパスワードだけで入れる状態なら攻撃者はそちらを狙い、パスキー方式の意味が失われる
- これらの設定はコード上で強制できないため、**管理画面を初めて公開する前に設定状況を確認し、確認できない場合は公開しない**(リリースのたびに変わる設定ではないため、毎回のリリース手順には組み込まない)
- 管理画面のURL・フォルダ配置(`specs/ikukyu/`配下か横断か)、OIDCリダイレクトのコールバックを静的エクスポートでどう受けるか、といった詳細は要件・設計フェーズで詰める。本ADRは認証とDB読み取りの方針までを確定させる

### 全アプリ共通の管理画面テンプレート

今後、別アプリで認証付き管理画面を作る場合は、以下をテンプレートとして**そのまま踏襲する**(アプリごとに認証方式を選び直さない)。

1. 認証はSupabase AuthのGoogle OIDCのみ。他の認証手段を足さない
2. 対象テーブル(`<アプリ名>_results`)に、運営者本人だけが全行SELECTできるRLSポリシーを追加する(アプリごとにテーブルが分かれているため、テーブル単位でポリシーを貼る。[ADR-0004](0004-agent-readonly-db-access.md)の読み取り専用ロール向けポリシーと同じ運用)
3. 管理画面は読み取り専用とし、編集・削除の経路を作らない
4. ログインに使うGoogleアカウントは、「パスキーを登録し、ログインはパスキーで行う」状態と、「2段階認証を有効にし、残るパスワード経路を保護する」状態の両方を維持する(上記のとおり別個の対策)。管理画面を初めて公開する前に設定を確認する
5. アプリ直属のパスキー(ネイティブWebAuthn)を実装したくなった場合は、このADRを更新してから行う(アプリごとに個別判断しない)

## 検討した代替案

| 候補 | 見送り理由 |
| --- | --- |
| Supabase Authのネイティブパスキー(beta) | `signInWithPasskey()`が提供されるが、beta・opt-in必須でAPIが変わりうる(GAは2026 Q2見込み)。パスキーを唯一の本番入口にするにはリスクがあり、Googleアカウント側をパスキー保護すればIdP経由で同じ目的(生体認証ログイン)を達成できるため見送り。将来ネイティブパスキーが必要になれば再検討 |
| Clerk + Supabase Third-Party Auth | ClerkのパスキーはGA・成熟しており、Supabaseとのネイティブ統合(2025/4〜)でRLSも通せる。ただし外部SaaSが1つ増える。利用者が本人のみでGoogle OIDCで足りる現状では過剰。複数管理者やアプリ直属パスキーが必要になれば再検討 |
| Cloudflare Access(①のみ) | URL単位のアクセス制御は強力だが②(DB読み取り)を解決しない。認証を通してもクライアントにSELECT権限のあるキーを置けないため、別途Supabase認証かサーバーが必要になり、単独では成立しない |
| Cloudflare Access + Supabase Edge Function(service_role) | ①②を両方解けるが、Edge Functionというサーバー部品が増え「サーバー機能を持たない」という[ADR-0001](0001-user-input-database.md)の前提から外れる。今回の用途には過剰 |
| 現状維持(Supabaseダッシュボード / ADR-0004の読み取り専用ロール) | 自作UIでの一覧・検索・スマホ閲覧というニーズを満たさない。人が見るだけなら足りるが、今回はUIを作りたいのが起点 |

## 影響

**良い点**
- 静的エクスポート構成を一切崩さず、①ページアクセスと②DB読み取りを1つのJWTで解決できる
- 追加の外部SaaSゼロ・betaに依存せず、当初要望(無料SaaSでOIDC＋パスキー体感)を満たせる
- [ADR-0001](0001-user-input-database.md)が予告していたSupabase Auth採用を具体化でき、他アプリの管理画面にも同じRLSパターンを再利用できる

**懸念点**
- RLSポリシーの絞り込みミスで、機微データ(月給・出産予定日)が意図しない認証ユーザーに露出しうる。メール一致条件を必ず検証し、`anon`でSELECTできないことも改めて確認してからリリースする
- 運営者メールをRLS条件に書く場合、アドレス変更時にポリシー更新が必要になる(運用で管理する)
- IdP(Google)への依存が生まれ、Googleアカウントを失うと管理画面に入れなくなる。ただし認証手段をOIDCの1本に絞る決定をした以上、フォールバックの認証経路(メールのマジックリンク等)を用意することは方針と矛盾するため設けない。復旧はGoogle側のアカウント復旧手段と、複数デバイスへのパスキー登録(バックアップ)によって担保する
- Googleアカウント側のパスキー登録・2段階認証はコードで強制できず、運用に依存する。設定が後から外されてもアプリ側は検知できないため、認証の強度は運営者の設定維持に委ねられる(これはIdP経由パスキー方式に内在する限界であり、アプリ直属パスキーを採用すれば解消できる。必要になった時点で本ADRを更新して再検討する)
- 機微データの閲覧経路が新設されるため、[specs/legal](../../specs/legal/requirements.md)のプライバシーポリシー更新要否を確認する
- これまで`anon`のINSERTしか使っていなかったため、Supabase Authの初期設定(OIDCプロバイダ登録・リダイレクトURL許可リスト等)が新たに必要になる
