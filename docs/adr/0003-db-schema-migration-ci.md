# 0003. DBスキーマ変更のコード管理とCIによる自動適用

## ステータス
提案中

## コンテキスト
- これまでSupabaseのテーブル作成・RLSポリシー設定はダッシュボードのSQLエディタで手作業しており、スキーマの実態がリポジトリに残らない(design.mdの記述が頼りで、実DBとの一致は保証されない)
- `specs/ikukyu/save-result`のテストフラグ(`is_test`)追加で初めて「既存テーブルへのスキーマ変更」が発生し、以下の課題が具体化した
  - 変更SQLをレビュー可能な形で残したい
  - 「カラム追加より先に新コードがデプロイされるとINSERTが失敗する(しかも保存はベストエフォートで握りつぶすため気づけない)」という適用順序の問題を、人間の手順記憶ではなく仕組みで保証したい
  - 「既存レコードの一括更新は1回きり」のような冪等でないSQLの二重適用を防ぎたい
- コードは既にmainマージでGitHub Actions(`deploy.yml`)から本番へ自動デプロイされており、スキーマ変更だけ手作業なのは運用が非対称

## 決定
**Supabase CLIのマイグレーション機能でスキーマ変更SQLを`supabase/migrations/`にコード管理し、`deploy.yml`にmigrateジョブを追加してmainマージ時に「マイグレーション適用 → ビルド・デプロイ」の順で自動適用する。**

- スキーマ変更は`supabase/migrations/<YYYYMMDDHHMMSS>_<変更内容>.sql`として作成し、アプリコードと同じPRでレビューする(命名・運用の詳細は`supabase/migrations/README.md`)
- 適用は`supabase db push`。適用済みファイルはDB内の管理テーブル(`supabase_migrations.schema_migrations`)に記録されるため、二重適用されない
- `deploy.yml`のdeployジョブは`needs: migrate`でマイグレーション完了を待つ。これにより「カラムがない状態で新コードが動く」順序逆転が起きない(逆方向=新カラムがあるのに旧コードが動く時間帯は、カラムに`default`を持たせることで許容する)
- 接続はGitHub Secrets `SUPABASE_DB_URL`(Session PoolerのURI)を使う。GitHub ActionsランナーはIPv6が使えず、Supabaseの直接続(db.<project>.supabase.co)はIPv6のため、IPv4対応のSession Pooler経由で接続する。DDLを流すためトランザクションモード(ポート6543)ではなくセッションモード(ポート5432)を使う
- ダッシュボードのSQLエディタでの手動スキーマ変更は今後行わない(マイグレーションと実DBの乖離を防ぐため)。データの調査・集計など読み取りはこれまでどおりSQLエディタでよい([data-check](../../.claude/skills/data-check/SKILL.md))

## 検討した代替案

| 候補 | 見送り理由 |
| --- | --- |
| 現状維持(design.mdにSQLを書きSQLエディタで手動実行) | スキーマがコードに残らず、適用順序・二重適用の防止が人間の手順記憶に依存する |
| コード管理のみ(適用はローカルから`supabase db push`を手動実行) | 適用履歴は管理されるがデプロイとの順序保証がなく、手動実行を忘れると本番だけ古いスキーマになる。CI化との差分が小さいわりに残る手作業が多い |
| Flyway / dbmate / Atlas などの汎用マイグレーションツール | 機能的には可能だが、Supabase CLIが同等機能を公式に持つため、ツールを増やす理由がない |
| `supabase link` + アクセストークンでの接続 | Secretsが2つ(ACCESS_TOKEN・DBパスワード)必要になり、リンク手順も増える。`--db-url`直指定ならSecrets1つで済む |

## 影響

**良い点**
- スキーマ変更がPRレビューの対象になり、変更履歴がgitに残る(再構築・障害調査に使える)
- マイグレーション→デプロイの順序と、二重適用の防止が仕組みで保証される
- 新しいアプリのテーブル追加(ADR-0001の「テーブル作成+定型RLSポリシー適用」)も定型のマイグレーションファイルのコピーで済むようになる

**懸念点**
- staging環境がないため、マージ=本番適用。破壊的変更(DROP・型変更など)はPRレビューで確実に見る必要がある(コードのデプロイも同じ信頼モデルのため、リスクの水準は従来と同等)
- `SUPABASE_DB_URL`はDBのフルアクセス権を持つ接続文字列であり、GitHub Secrets以外(リポジトリ内・ログ)に絶対に出さない
- migrateジョブが失敗するとデプロイもブロックされる(意図した挙動だが、Secrets未設定・Supabase一時停止でも止まる点に注意)
- 既存スキーマ(`ikukyu_results`本体・RLSポリシー)はまだコード化されていない。必要になったら`supabase db pull`でベースラインとして取り込む(今回のスコープ外)
