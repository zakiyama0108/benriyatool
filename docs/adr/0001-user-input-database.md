# 0001. ユーザー入力結果を保存するDB/BaaSの選定

## ステータス
提案中

## コンテキスト
- `ikukyu`（育休シミュレーター）で、ユーザーが入力した内容とシミュレーション結果をDBに登録したい
- 用途は2つ: ①ユーザー自身が後で結果を見返せるようにする、②運営者が匿名の入力データを集計・分析する
- ログイン機能はなく、今後も導入予定はない。レコードごとに一意なIDが振られれば十分で、「同一ユーザーの複数レコードを紐付ける」ための永続的なユーザー識別子は不要
- 現在サイトはNext.jsの静的エクスポート（`output: "export"`、[next.config.ts](../../next.config.ts)）でCloudflare Workersに静的配信されており（[wrangler.toml](../../wrangler.toml)）、サーバー機能（API Route/Route Handler、Cloudflare Pages Functions等）は一切ない。DB導入にあたってもこの静的配信構成を維持し、サーバー機能を新設しない方針とする
- 今後 `ikukyu` 以外のアプリ（`app/<アプリ名>/`として追加される想定）でも同様にDBを使う可能性があるため、1アプリに閉じない再利用可能な構成にしたい
- 個人開発の小規模運用が前提で、無料枠に収まる範囲で運用したい。保存するのは月給・予定日などの入力値のみで、氏名・メールアドレス等の直接的な個人識別情報は含まない

## 決定
**Supabase（PostgreSQL + PostgREST + Row Level Security）を採用し、ブラウザから`@supabase/supabase-js`経由でanon keyを使い直接INSERTする。**

- サーバー機能を追加せず、現状の静的配信構成のまま実現できることを最優先で選んだ
- 書き込みの安全性はRLS（Row Level Security）で担保する。テーブルごとに以下のポリシーを設定する
  - `anon`ロールは `INSERT` のみ許可する
  - `SELECT` / `UPDATE` / `DELETE` は `anon` に許可しない（他人のレコードの閲覧・改ざん・削除ができないようにするため）
- ユーザーが自分の結果を見返す機能は、INSERT時にSupabaseが払い出す`id`（uuid）を使ったレコード単位の再表示（例: `/ikukyu/result/[id]`のような共有リンク）で実現する。ユーザーを横断的に識別するIDは持たせない
- 運営者の集計・分析は、Supabaseダッシュボードのテーブルエディタ/SQLエディタから行う。`anon`キーはクライアントに公開される前提の値であり、集計用の`service_role`キーは絶対にクライアントに含めない
- 複数アプリでの再利用は、Supabaseプロジェクト自体は1つを使い回し、アプリごとにテーブルを分ける（例: `ikukyu_simulator_results`）。プロジェクトを分けない理由は、無料プランのプロジェクト数制約を節約し、管理を一元化するため
- 各アプリのDB書き込み処理は `app/<アプリ名>/lib/` に薄いラッパー関数としてまとめ、UIコンポーネントから直接Supabaseクライアントを呼び出さない。特定のBaaSへの依存箇所を1ファイルに閉じ込め、将来の移行や単体テスト時のモック差し替えをしやすくするため

## 検討した代替案

| 候補 | 見送った理由 |
| --- | --- |
| Firebase Firestore（NoSQL） | クライアント直接書き込み + セキュリティルールという構成はSupabaseと同等に実現できるが、将来の集計・分析はSQLの方が定型化しやすく、他アプリ追加時も「テーブルを増やすだけ」で拡張できるRDBを優先した |
| Cloudflare D1 | 無料枠は魅力的で`wrangler.toml`との親和性も高いが、ブラウザから直接アクセスする手段がなく、利用にはCloudflare Pages Functions等のサーバー処理が必須。「静的配信を維持する」という前提と矛盾するため見送り。将来サーバー機能を持たせる決定をした場合の有力な再検討候補として残す |
| Turso（libSQL） | HTTP経由でのアクセスは可能だが、SupabaseのRLSほど柔軟な行レベルアクセス制御がなく、匿名クライアントに配布する書き込み用トークンの権限を安全に絞り込む標準的な方法がない |
| Vercel Postgres / Neon | 基本はPostgresプロトコルでの接続が前提で、ブラウザから安全に直接書き込む標準的な方法がない（サーバー層が必要になる） |

## 影響

**良い点**
- サーバーレスで完結し、インフラ管理・追加のホスティングコストがほぼゼロ
- RLSにより「書き込みのみ・閲覧不可」という最小権限をDB側で強制でき、静的サイトからの直接アクセスでも安全性を確保しやすい
- SQL（Postgres）なので、将来の集計・レポーティングや、他アプリ追加時のテーブル追加が定型的にできる
- 1つのSupabaseプロジェクトを複数アプリで使い回せるため、アプリを追加するたびにDBを選定し直す必要がない

**懸念点・実装時に対応が必要な事項**
- Supabase無料プロジェクトはAPIアクセスが一定期間（目安1週間）ないと一時停止される。対策として、GitHub Actionsで週次のヘルスチェックping用ワークフローを追加することを検討する（既存の`.github/workflows/`にスケジュール実行を1つ追加する想定）
- `anon`キーはクライアントバンドルに含まれる前提の値だが、RLSポリシーの設定を誤ると全データが閲覧・書き込み可能になってしまう。テーブル作成時は必ずRLSを有効化し、`anon`ロールでSELECTできないことをテストで確認してからリリースする運用ルールとする
- `anon`キーからの`INSERT`はレート制限が標準では弱く、悪意のある大量投稿（スパム）を防ぐ仕組みが別途必要になる可能性がある。実際に問題が起きた場合はCloudflare TurnstileなどのCAPTCHA導入を検討する
- 500MB（無料枠）を超える、またはSupabase自体をやめる場合の移行に備え、前述の通りDBアクセスは`app/<アプリ名>/lib/`のラッパーに閉じ込め、Supabase固有のAPIがUIコンポーネントに漏れないようにする
- 月給・予定日等の入力データを保存する取り扱いになるため、[specs/legal/requirements.md](../../specs/legal/requirements.md)のプライバシーポリシー（収集情報・利用目的）の更新が必要になる。DB保存機能を実装するfeatureのタスクに、プライバシーポリシー更新を含めること
