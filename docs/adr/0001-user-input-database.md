# 0001. アプリ横断で使うDB/BaaSの選定

## ステータス
提案中

## コンテキスト
- べんりやつーる配下の各アプリ（現在: 育休シミュレーター、今後も追加予定）で、ユーザーの入力内容と結果をDBに保存したい。特定の1アプリではなく、今後追加するアプリでも同じ仕組みをそのまま使い回せることを前提に選定する
- 用途はアプリによって異なりうるが、代表例（育休シミュレーター）では①ユーザー自身が後で結果を見返せるようにする、②運営者が匿名の入力データを集計・分析する、の両方を想定している。DBの設計はどちらか一方しか使わないアプリにも対応できる必要がある
- ユーザー識別の要件はアプリによって異なる。育休シミュレーターのような匿名利用アプリはレコード単位のIDで足りるが、今後ログイン機能を持つアプリを追加する可能性もある。DBの選定はどちらのパターンにも対応でき、ログイン機能を後から追加する際にDBを選び直さずに済む必要がある
- サイトはNext.jsの静的エクスポート（[next.config.ts](../../next.config.ts)）でCloudflare Workersに配信（[wrangler.toml](../../wrangler.toml)）しており、サーバー機能は一切ない。この構成は維持する
- 個人開発の小規模運用が前提。無料枠に収まる範囲で運用したい

## 決定
**Supabase（PostgreSQL + RLS）を全アプリ共通の1プロジェクトとして採用し、ブラウザから`anon`キーで直接INSERTする。**

- RLS: `anon`ロールは`INSERT`のみ許可し、`SELECT`/`UPDATE`/`DELETE`は許可しない（他人のレコードを閲覧・改ざんできないようにするため）
- テーブルはアプリごとに`<アプリ名>_results`として作成する。1レコード＝1回の入力＋結果とし、共通カラムとして`id`（uuid）・`created_at`を持つ
- ログイン不要なアプリでは、INSERT時に払い出される`id`を使った個別URL（例: `/<アプリ名>/result/[id]`）で結果を見返す。ユーザーを横断する識別子は持たせない
- ログインが必要なアプリを追加する場合は、Supabase標準の認証機能（Supabase Auth）を使う。`user_id`カラムを`auth.users`に紐付け、RLSで`auth.uid() = user_id`のときだけ本人に`SELECT`/`UPDATE`を許可すればよく、DB/BaaS自体は選び直さずに済む
- Supabaseクライアントの初期化は`app/lib/supabaseClient.ts`に共通化する。各アプリは`app/<アプリ名>/lib/`にテーブル固有の薄いラッパー関数を置き、そこからこの共通クライアントを呼ぶ
- 集計・分析は`service_role`キーを使いダッシュボード/SQLエディタから行う（クライアントには含めない）
- 新しいアプリでDBを使う場合の追加作業は「テーブル作成＋定型のRLSポリシー適用」だけで済むようにする

## 検討した代替案

| 候補 | 見送り理由 |
| --- | --- |
| Firebase Firestore | クライアント直書きは同等に可能だが、複数アプリ分の集計はSQLの方が扱いやすく、アプリ追加時もテーブル追加だけで拡張できるRDBを優先した |
| Cloudflare D1 | ブラウザから直接アクセスできずサーバー処理が必須。静的配信を維持する前提と矛盾するため見送り（将来サーバー機能を持つ決定をした場合の再検討候補） |
| Turso | 匿名クライアントに配布する書き込みトークンを、SupabaseのRLSほど安全に絞り込む標準的な方法がない |
| Vercel Postgres / Neon | ブラウザから安全に直接書き込む標準的な方法がない（サーバー層が必要） |

## 影響

**良い点**
- 全アプリで1プロジェクト・1つの共通クライアント初期化を使い回せ、アプリ追加のたびにDBを選定し直さなくてよい
- RLSで「書き込みのみ・閲覧不可」を強制でき、静的サイトからの直接書き込みでも安全性を確保できる
- SQLなので、複数アプリ分のデータを横断した集計・レポーティングもしやすい
- Supabase Authが同じPostgres基盤に含まれるため、匿名利用のアプリと将来ログインが必要なアプリのどちらも同じDBで対応でき、後からDBを選び直す必要がない

**懸念点**
- 無料プロジェクトはAPIアクセスが一定期間（目安1週間）ないと一時停止される。GitHub Actionsでの週次ヘルスチェックpingを検討する
- RLSポリシーの設定ミスで全データが露出しうる。テーブル作成時は必ずRLSを有効化し、`anon`でSELECTできないことを確認してからリリースする
- `anon`からの大量投稿（スパム）対策は標準では弱い。問題が起きたらCloudflare Turnstile等の導入を検討する
- アプリごとの入力データ内容によっては、そのつど[specs/legal/requirements.md](../../specs/legal/requirements.md)のプライバシーポリシー更新要否を確認する
