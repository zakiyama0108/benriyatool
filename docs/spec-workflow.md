# 仕様作成の3ステップ

- **Step1 requirements.md(要件定義)**
  「何を作るか(WHAT)」「なぜその仕様にしたか(根拠)」を言語化する。数式・変数名は使わず日本語の言葉で書く(正確な計算式はコードとテストに委ねる)。技術的な実装方法(HOW)はここでは書かない。
  以下の見出しをテンプレートとして使う(該当しないものは省略してよい)。

  1. **概要** — 機能名・目的・優先度
  2. **ユーザーストーリー** — 「〜としては、〜したい」という利用者視点の要求
  3. **機能要件** — 実装する機能と入出力を言葉で説明する
  4. **ビジネスルール** — 数値・条件などのルールと、その根拠(法令・公式資料・過去の意思決定など)を必ずセットで書く。項目が複数ある場合は`###`見出しで分ける(テストとの対応付けがしやすくなる)
  5. **エッジケース・例外処理** — 特殊な入力やエラー時にどう振る舞うべきか
  6. (任意)**非機能要件・依存関係・制約条件・UI/UX要件** — 関係する場合のみ書く。無理に埋めない

- **Step2 design.md(設計)**
  requirements.mdのビジネスルールを「どんな手順・分岐で処理するか」を日本語の文章(変数名・数式なし)で書く**処理フロー**に絞る。フォルダ構成・使用技術はCLAUDE.md/requirements.mdで足りるため書かない。型定義・画面レイアウトは実装に委ねる(非自明なUIパターンがある場合のみrequirements.mdのUI/UX要件に書く)。分岐・複数ステップのロジックが1つもない機能(例: 純粋なルーティング変更)は、design.md自体を作らずrequirements.mdのみで完結してよい。
  以下の構成をテンプレートとして使う。

  1. **処理フロー** — `##`見出し。個々の処理はこの下に`###`見出しで並べる
  2. **処理の呼び名**(`###`見出し) — 業務的な言葉にする(✗「calcPapaChildcare67の変更」 → ○「通常育休(前期67%)の開始日を決める処理」)。関数名・実装対象ファイルなどの実装詳細はtasks.mdに書く
  3. **対象** — この処理が何に対して行われるか
  4. **手順** — 日本語の文章で書く番号付きステップ(変数名・数式は使わない)。分岐がある場合は「〜の場合は…、そうでない場合は…」と書く。単純な1つの計算(例:「出産予定日の42日前」)のようにビジネスルールの文章だけで手順が自明なものは書かない
  5. **関連するビジネスルール** — `requirements.md#見出し`

- **Step3 tasks.md(タスク分解)**
  設計をもとに実装可能な最小単位に分解する。対象の関数名・ファイル名などの実装詳細はここに書いてよい。タスクを細かく分けるほどAIの生成精度が上がりレビューもしやすくなる。

# テストとの対応付け

- テストの`// 仕様: specs/.../requirements.md#見出し`コメント(書き方は @docs/test-comment-guideline.md)は、基本的にrequirements.mdの機能要件・ビジネスルール見出しを参照する。design.mdの処理フローは、requirements.mdで既にテストされているロジックを実装向けに書き下したものなので、原則テストからは参照しない。
- ビジネスルールの箇条書きは「〜の場合、〜になること」という文体に揃えておくと、そのままテストの`it()`に転記しやすい。
- `npm run check:spec-coverage`で、requirements.md/design.mdの各項目に対応するテストが書けているかを棚卸しできる。design.mdの処理フロー項目はテストから参照されないのが正常なので、❌が出ても気にしなくてよい。
